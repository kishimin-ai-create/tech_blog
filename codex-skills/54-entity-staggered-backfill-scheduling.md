# Entity単位の初回バックフィルを分割し、開始時刻をずらす設計

## 結論

初回バックフィルは、全Entityを1回の長時間プロセスで処理するのではなく、Entityごとのジョブへ分割する。各ジョブは同時に1件だけ実行し、開始時刻をずらす。1つのEntityの投稿数が多い場合は、さらに短いスライスへ分割し、DBへ保存したカーソルから再開する。

これは、数時間連続するアクセスを避けながら、全件取得を途中で諦めずに進めるための設計案である。本記事の内容は実装済みの機能ではない。

## 背景

既存の収集処理は記事を保存するたびにDBへ書き込み、一意制約によって同じ記事の重複保存を防いでいる。一方で、Entity単位の進捗や次回のページ位置は永続化していない。そのため、途中で停止して再実行すると、先頭付近から既存記事を確認し直すことになる。

待ち時間を設定していても、既存記事の再確認を含む総リクエスト数が増えれば、処理時間と相手側への累積負荷は増える。長時間の連続実行を避ける方針と、過去の記事を最後まで取得する要件を同時に満たす必要がある。

## 解決したい課題

- 全Entityの処理を数時間連続させない。
- 中断後に先頭ページから調べ直す量を減らす。
- Entityごとの進捗、失敗、完了をDBから確認できるようにする。
- 初回バックフィル完了後に、日次の差分収集へ安全に切り替える。

## 前提・制約

- HTTPリクエストは並列化せず、逐次実行する。
- 初回バックフィルと日次差分収集は同時に実行しない。
- 収集対象を特定できる名称、URL、HTML構造は、通常ログや公開文書へ出さない。
- Entity候補を完全に発見できたと確認できない間は、全件取得完了と宣言しない。

## 検討した選択肢

### Option A：全Entityを1回のプロセスで取得する

全体の一覧から順にEntityをたどり、最後まで同じプロセスで処理する方式である。

#### メリット

- ジョブテーブルや再開カーソルを追加せずに始められる。
- 正常終了すれば、処理の入口と終了が1回で済む。

#### デメリット

- 実行時間と総リクエスト数の上限を設けにくい。
- PC再起動や通信障害の後、進捗が分からない。
- 失敗したEntityだけを再実行しにくい。

### Option B：Entityごとのジョブを開始時刻をずらして実行する

Entityごとにジョブを登録し、実行可能時刻になったジョブを1件ずつ処理する。1回の実行にも時間またはページ数の上限を設け、終了時に次回カーソルを保存する。

#### メリット

- 同時実行Entity数を1件に固定し、相手先への瞬間的な負荷を抑えられる。
- 1回の実行時間を運用上限内に収められる。
- Entity単位で再試行、停止、完了を管理できる。

#### デメリット

- ジョブ状態、lease、カーソル、次回実行時刻の永続化が必要になる。
- 一覧の挿入や削除で、数値ページだけのカーソルがずれる可能性がある。
- 全Entityの完了判定と日次収集への切り替え条件が増える。

## 評価軸

| 評価軸 | Option A | Option B |
| --- | --- | --- |
| 連続アクセス時間 | 長くなり得る | スライス上限を設定できる |
| 中断後の再開 | 先頭からの確認が発生し得る | 保存カーソルから再開できる |
| Entityごとの失敗管理 | 実行ログに依存する | DBの状態で追跡できる |
| 実装量 | 少ない | ジョブ状態の追加が必要 |
| 相手先負荷の調整 | 全体で調整しにくい | Entity間の休止を設定できる |

## 最終判断

Option Bを採用する。初回バックフィルをEntity別ジョブとして登録し、同時実行は1件に制限する。ジョブは開始時刻をずらし、1回のスライスが最大実行時間または最大ページ数へ到達したら正常に中断する。

初期値の候補は次のとおりである。これらは設計上の提案であり、本番設定として確定した値ではない。

| 項目 | 初期値の候補 |
| --- | --- |
| 同時実行Entity数 | 1 |
| 1スライスの最大時間 | 15分 |
| 1スライスの最大ページ数 | 20ページ |
| リクエスト間隔 | 5秒 + 0〜3秒の揺らぎ |
| Entity間の最低休止時間 | 30分 |
| 同じEntityの次回実行 | 翌日以降 |

## ジョブとカーソルの責務

ジョブには、少なくとも次の状態を保存する。

```text
entity_id
archive_path
next_page
last_record_key_hash
status
next_run_at
lease_expires_at
failure_count
last_http_status
last_success_at
completed_at
```

`next_page`だけでは、一覧に新しい記事が挿入されたときの位置ずれを検出できない可能性がある。そこで、直前に確認した記事識別子の不可逆ハッシュも保存し、再開時に次ページの境界を検証する。期待した境界と一致しない場合は自動で取り直さず、ジョブを人間の確認待ちにする。

記事の保存とカーソル更新は同じページの処理が完了した後に行う。ページ途中で停止しても、カーソルだけが先に進んで記事を取りこぼす状態を避けるためである。

## 実行シーケンス

1. 実行可能時刻を迎えたジョブを1件選ぶ。
2. DBロックとジョブleaseを取得し、状態を`running`へ変更する。
3. 保存済みのカーソルから一覧を逐次取得する。
4. 一覧上の識別子をDBと照合し、必要な詳細だけを取得する。
5. 記事と関連情報を保存する。
6. ページ完了後に次回カーソルと実行結果を保存する。
7. 続きがあれば`paused`、次ページがなければ`completed`にする。
8. leaseとロックを解放し、次のEntityとの間隔を空ける。

`429`を受けた場合は新しいHTTPアクセスを停止し、レスポンスの再試行時刻を次回実行へ反映する。待ち時間を短くして遅れを取り戻すことはしない。タイムアウトや一時的なサーバーエラーは、既定回数の再試行後に`retry`へ移す。

## 完了条件と日次収集への切り替え

記事件数が増えたことだけでは、初回バックフィルの完了とはみなさない。発見済みの全Entityジョブが`completed`であり、未処理や失敗の状態が残っていないことを確認する。さらに、Entity候補の発見範囲と未確認事項を記録し、同じ条件の再確認で未登録記事がないことを確認する。

これらを満たすまで、日次差分収集へ切り替えない。初回取得が未完了のまま日次処理を始めると、現在の一覧で登録済みの記事に到達した時点で停止し、過去の未登録記事を見落とす可能性がある。

## 実装後の結果

未実装の設計案であるため、Entity別ジョブ、カーソル、開始時刻の分散、完了判定による動作結果は未確認である。確認できているのは、既存の長時間バックフィルでは記事保存の重複は抑止できても、詳細ページの再取得までは抑止できないという点である。

## トレードオフ・今後の懸念

- Entity別に分割すると、ジョブ状態を保守する実装量が増える。
- 一覧構造が変わった場合、カーソルの再構築が必要になる。
- Entity候補の発見元が不完全なら、ジョブを全件完了しても全体の全件取得とは言えない。
- 1日の最大スライス数、実行順序、完了済みジョブの保持期間は未決定である。
- 利用条件や`robots.txt`など、技術的な待ち時間とは別の確認も必要である。

## まとめ

Entity単位の初回バックフィルは、同時実行数を増やして短縮するより、ジョブを分割し、開始時刻とスライスを制御する方が運用しやすい。永続カーソルによって中断後の再開点を明確にし、Entityごとの状態を管理することで、全件取得の進捗と相手先への負荷を別々に観測できる。

この方針はまだ設計段階である。実装する際は、ジョブ状態、カーソル境界、`Retry-After`、完了条件をテストで固定してから導入する。
