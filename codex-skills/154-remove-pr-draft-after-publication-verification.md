# PR本文の一時Markdownは、公開内容を確認してから削除する

## 結論

PR作成後に本文の一時Markdownを残さない運用を、公開Skillの後処理へ追加した。削除するのは、そのPRへ渡した未追跡の本文ファイル1件だけである。GitHub上のタイトル・本文・base/headを確認できない場合は保持する。

対象は2026年10月22日に更新した`pull-request-writing`と`github-create-pull-request`。これはSkillの指示変更であり、GitHubが自動でローカルファイルを削除する機能ではない。

## 背景と制約

本文作成とGitHub公開は、既存のADR-0023により別Skillへ分かれていた。本文作成側は差分からドラフトを作り、公開側は確定文を改変せずGitHub MCPへ渡す。その後、利用者から「PRを作った後に、mdを削除する」よう依頼された。

リポジトリにはPR以外のMarkdownや、Gitで追跡された過去の本文もある。拡張子だけで削除対象を決めると、今回の一時ファイルとは無関係な文書まで消してしまう。

## 採用した境界

本文作成だけなら保存したドラフトを保持する。PR公開が依頼されたときは、タイトルと本文に加えて、その入力ファイルのパスも公開Skillへ引き渡す。

公開SkillはPR作成後にGitHub MCPから公開内容を取得し、repository、base/head、タイトル、本文を照合する。削除直前にローカルファイルも読み直し、改行コードの違いを除いて本文が一致することを確認する。公開後に編集された内容は削除しない。

| 状態 | 一時Markdownの扱い |
| --- | --- |
| 新規作成成功・公開内容一致・未追跡の入力ファイル | 正確なパスを指定して削除 |
| 作成失敗・公開内容を確認できない | 保持 |
| 重複PRを見つけただけ | 保持 |
| Gitで追跡済み・保持指定あり | 保持 |
| 公開後に本文が編集された | 保持 |
| 当該ファイルが既にない | 不在を報告。他のファイルは削除しない |
| ローカル削除だけ失敗 | PRの成功と削除の失敗を分けて報告 |

削除に失敗してもPR作成を再実行しない。外部操作の成功とローカル後処理の成功は別々に扱う。

## 既存指示との整合

確認中、本文作成SkillにGitHub CLIで公開する古い手順が残っていた。今回、その節を専用Skillへの引き渡しに変更し、既存ADRと公開SkillのGitHub MCP限定の境界へ揃えた。本文作成側が独自に公開や削除を行う経路を増やしてはいない。

Gitのコミット・pushやコード変更を公開Skillが行わない制約も維持した。

## 確認した結果と限界

両Skillは`skill-creator`の`quick_validate.py`で成功し、差分の空白エラーもなかった。指示を読み合わせ、成功時だけ削除すること、追跡済みファイルと失敗時の本文を保持すること、CLI公開の矛盾がないことを確認した。

今回のPR #6用本文`pull-request/bump-version-1-0-5.md`は、確認時点で既に存在しなかった。この変更によって削除したとは報告しない。新しい指示を使った次のPR作成と実ファイル削除の一連の動作は、まだ実行していない。

この運用には、内容を照合できない場合に一時ファイルが残る制約がある。失敗時にも一律に消すことより、再確認に使う本文を保持する判断を採用した。
