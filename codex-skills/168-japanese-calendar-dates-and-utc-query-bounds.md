# 日本の日付をUTCとして検索すると朝の記事が漏れた原因

## 結論

日付入力は`Asia/Tokyo`の暦日として解釈し、検索条件を作る時点でUTCへ変換した。保存済みデータと返却する時刻の表現はUTCを維持した。

## 発生した問題

期間内の記事を全件返すAPIを追加した際、最初は開始日00:00と終了日23:59:59.999999をUTCとして検索していた。利用者から「日本時間でくるから対応して」と指摘を受けた。

### 症状

「10月1日」の指定が、日本では10月1日09:00から10月2日09:00直前の期間になっていた。日本時間の朝の記事が漏れ、翌日の記事が入り得る条件だった。

### 発生条件

2026年10月24日、Python 3.14.7、FastAPI、SQLAlchemyを使うslope-collector。DBへ保存する記事時刻は既にUTCだった。

### 影響

件数上限を外しても、検索する期間自体がずれていれば、利用者が求める全件にはならない。

## 調査

日付範囲APIは`tzinfo=UTC`で境界を作っていた。一方、既存の収集側は`ZoneInfo("Asia/Tokyo")`で入力時刻を解釈してからUTCへ変換していた。今回の修正では検索側を同じタイムゾーンへ揃えた。

## 原因

`YYYY-MM-DD`には時差情報がない。保存時刻がUTCであることを理由に、入力された日付の意味までUTCと決めてしまった。入力の日付と保存形式を別々に確認できていなかった。

## 解決方法

開始側では次のように、日本の午前0時をUTCへ変換する。

```python
start = datetime.combine(
    from_date, time.min, tzinfo=ZoneInfo("Asia/Tokyo")
).astimezone(UTC)
```

終了側も同じタイムゾーンの`time.max`をUTCへ変換し、`published_at <= end`で絞り込む。2026年10月1日から7日なら、UTCでは9月30日15:00から10月7日14:59:59.999999となる。

## 動作確認

テストでは変換関数で期待値を作らず、保存されるUTC時刻を具体値として用意した。

| 保存済みのUTC時刻 | 日本時間での意味 | 対象 |
| --- | --- | --- |
| 9月30日14:59:59.999999 | 開始の直前 | 除外 |
| 9月30日15:00 | 10月1日00:00 | 含む |
| 10月7日14:59:59.999999 | 終了日の最後 | 含む |
| 10月7日15:00 | 10月8日00:00 | 除外 |

修正前は3ケースが失敗した。修正後は、年越し、単日指定、絞り込み、入力検証を含む専用APIの19ケースが成功した。全体は278件成功した。検証は匿名データのSQLiteとASGI経由で行い、実MySQLやデプロイ環境では未検証である。

## 再発防止

日本の暦日がUTCの前日へまたがる境界を回帰テストへ残した。OpenAPIのパラメーター説明とREADMEにも`Asia/Tokyo`を記載した。既存のページ分割APIの日付仕様は今回変更していない。

## 得られた教訓

時刻の保存形式と、利用者が入力する日付の意味には別の契約が必要だった。UTCへ保存していても、検索期間の境界は利用者の暦日に基づいて作る必要がある。
