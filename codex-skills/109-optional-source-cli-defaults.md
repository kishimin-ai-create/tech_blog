# CLIの取得元を追加するときに選択肢と既定値を分ける

## はじめに

既存の二つの取得元に、明示選択できる追加取得元を実装した。この記事は、CLIで受け付ける選択肢を増やしながら、未指定時の処理範囲を保った変更記録である。取得元名、人物、実URL、セレクタは掲載しない。

## 背景・目的

設定読み込みと取得処理は取得元ごとの接頭辞を扱えたが、CLIの選択肢と型は二つに限られていた。追加取得元の通常ページと手動アーカイブを利用できるようにし、既存コマンドに追加設定を必須としないことが必要だった。

## 当初の想定

既存の汎用処理を使って取得元を追加する方針だった。定期コマンドの既定対象も自動的に増やすという依頼はなかった。

## 実際にやったこと

`app/collector.py` で既定値と選択可能な値を分け、`app/config.py` の取得元型を広げた。次は実装の定義であり、値は内部の汎用キーである。

```python
SOURCE_KEYS = ("source_a", "source_b")
AVAILABLE_SOURCE_KEYS = (*SOURCE_KEYS, "source_c")
```

追加取得元の非公開設定は明示選択時に読み込む。`.env.example` には空の設定項目を加えた。既存の通常取得・アーカイブ処理を再利用し、サイト固有のURLやパーサー分岐は追加していない。

## 実際の結果

| 呼び出し | 確認した挙動 |
| --- | --- |
| 取得元未指定 | 既存の二つを選択 |
| `--source source_c` | 追加取得元のみを選択 |
| 手動バックフィルとアーカイブ設定 | 追加取得元のアーカイブ経路へ委譲 |
| 追加設定の不備 | 設定値を含めない検証エラー |

**FACT:** `tests/small/test_collector.py` と `tests/medium/test_config.py` で上記の境界を検証した。アーカイブの永続化テストでは同じ対象行、非アクティブ状態、再実行時の詳細要求省略を確認した。選択した実対象でも通常取得とアーカイブ保存を確認した。

## 良かったこと

既存処理を使うことで、追加取得元にも同じ保存・チェックポイントの契約を適用できた。

## うまくいかなかったこと

簡易検証で一ページを一記事と取り違え、期待したレコード数のアサーションが失敗した。実際の一覧を確認し、記事キー集合で照合し直したところ保存結果は一致した。ページ数だけで保存件数を決めない。

## 想定との差

取得元の追加自体は既存経路で実現した。初回の検証期待値には誤りがあったが、保存不具合とは区別して修正した。全対象の取得品質や性能は検証していない。

## 学んだこと・次回の方針

**INFERENCE:** 選択肢と既定値を別に管理すると、新しい設定を導入する時期と、定期処理へ組み込む時期を分けられる。取得元を増やす際は、型、CLI、選択時の設定読み込み、通常・アーカイブ経路、未指定時の挙動を確認する。
