# 期間内の記事を全件返すために専用APIを追加した理由

## 結論

期間内の記事をすべて取得するために、`GET /records/by-date`を追加した。既存の`GET /records`はページ分割を維持した。全件取得の対象は保存済みの記事であり、外部サイトから不足分を収集するAPIではない。

## 背景

2026年10月24日のslope-collectorでは、`/records`に日付を指定しても、既定20件、最大100件の1ページだけが返った。利用者から「日付の範囲指定では範囲内を全件取得したい」という要望があった。

## 解決したい課題

日付による絞り込みと、応答件数の制限は別の条件だった。期間を指定しただけでは、その期間の記事をすべて取得したことにはならなかった。

## 前提・制約

- Python 3.14.7、FastAPI、SQLAlchemyを使う開発環境限定の確認API。
- 本文付きの保存済み記事を取得する。新たな収集やDB移行は行わない。
- 既存のページ分割を使う利用者の契約を維持する。

## 検討した選択肢

### Option A：全件取得用のAPIを追加する

`from`と`to`を必須にして、意図した期間の全件取得を明示する。

#### メリット

呼び出すURLから取得方法が分かり、通常の一覧の件数制限を維持できる。

#### デメリット

確認するAPIが増える。選択した期間が広ければ応答も大きくなる。

### Option B：既存APIの日付指定時だけ件数制限を外す

#### メリット

既存URLのまま全件を取得できる。

#### デメリット

日付パラメーターの有無で、既存APIの応答件数に関する意味が変わる。

## 評価軸

| 評価軸 | 専用API | 既存APIの制限解除 |
| --- | --- | --- |
| 期間内全件の取得 | 可能 | 可能 |
| 既存のページ分割契約 | 維持 | 日付指定時に変更 |
| 入口の追加 | 必要 | 不要 |

## 最終判断

利用者がOption Aを選択した。`GET /records/by-date?from=2026-10-01&to=2026-10-07`は、本文を含む`records`配列を返す。`entity_id`による絞り込みも受け付ける。

## なぜこの選択をしたか

ページを表示したい処理と、期間のデータをまとめて使いたい処理を、それぞれの呼び出しで明示できるためだ。取得対象の網羅性と応答の大きさを同じ設定へ押し込めずに済む。

## 実装後の結果

107件の期間内記事を返すHTTPテストが成功した。100件を超えるデータを用意し、IDの全順序まで照合した。既存の一覧は既定20件と最大100件のページ分割を維持し、詳細URLも引き続き利用できる。

新しい固定パスは`/records/{record_id}`より先に登録した。専用URLが存在しなかった最初のテストでは、`by-date`が記事IDとして検証されてHTTP 422となった。

## トレードオフ・今後の懸念

全件応答には件数上限を設けていない。大きな期間の実データで応答時間やメモリー使用量は測定していない。一定量ずつ取得したい用途には既存の`/records`を使う。

## 今回の判断を使う条件

この構成は、保存済みデータを明示した期間でまとめて使いたい場合の選択である。無制限の公開APIを推奨するものではなく、今回の開発用ローカル境界を前提としている。
