# 既存スキルとの照合で存在しないIDを検出する

## 結論

モデルが既存スキルの一覧から候補を選ぶ処理では、一覧にないIDを返すことがある。照合結果をカタログと照らし、不正な結果だけを回数を制限して再生成し、毎回検証することで、不明なIDをそのまま採用せずに処理を継続できる場合がある。

## 発生した問題

プロンプト定期分析では、繰り返された依頼の候補を既存スキルと照合し、既存機能で対応済みの提案を除外する。大量の履歴を分類する修正後の実データ検証でも、照合で `Invalid skill matches` が発生した。

後の診断では、ある候補についてモデルが返した8件のスキルIDのうち3件が、入力したカタログに存在しなかった。同じ候補の再試行は有効な5件を返した。前の失敗も同じ理由だったかは、詳細が残っていないため分からない。

## 対応

候補ごとに照合し、その候補に紐づく根拠だけを後続のレビューに渡す。照合結果は候補indexの範囲と一意性、スキルIDの存在と重複を検証する。不正な照合応答は最大3回再生成し、そのたびに同じ検証を適用する。提案のレビュー結果にも独立した検証と1回の修復を設けた。

存在しないIDを勝手に候補から削除して成功扱いにすると、既存スキルを見逃して重複提案を出す可能性がある。再試行後も検証できなければ失敗として扱う。

## 動作確認

回帰テストには、存在しないIDが続いた後に有効な結果を返すケースと、候補ごとに根拠を分けて渡すケースを追加した。テスト全体68件とmypy strictは成功した。

2026年11月6日の実データ283件を使った通知なし検証では、分類からスキル照合まで12分49秒で完了した。この確認だけでは定期タスクの通知成功を意味しない。

## 制約

有効なIDが返っても、意味的に最適なスキル選択かどうかはモデルの判断に依存する。再試行には時間がかかり、20分の定期タスク制限を超えない保証はない。元の通知は例外の型のみを残していたため、後続の再現例と元の障害を同一原因とは断定できない。

根拠: `prompt-inventory` の `skill_proposals.py`、`tests/test_skill_proposals_medium.py`、コミット `4ebf587`。
