# 全件取得の確認では件数だけでなく記事IDの集合を比べる

## はじめに

取得処理の完了ログとAPIの件数が一致していても、記事の取り違えがないとは限らない。今回は全件取得の後に、一覧で観測した記事IDとDBに保存した記事IDの集合を照合した。

対象別件数、実際のID、対象名、記事内容は公開しない。検証方法と観測結果だけを記録する。

## 前提・環境

PythonとSQLAlchemyでローカルDBを照会した。記事一覧を読むときにIDをローカルの一時記録へ残し、取得後に同じ対象の保存済みIDを取り出した。記事明細を含む記録は公開リポジトリへ入れていない。

## やってみた結果

**FACT:** 今回取得した履歴について、一覧とDBの記事ID集合が一致した。欠落と余分なID、保存行内の重複は0だった。対象外の既存データの件数と対象状態も変わらなかった。

再実行では新規保存が0になり、既存記事の詳細リクエストも0だった。この確認は件数の一致とは別の観測である。

## 実装・検証

### 集合と重複を別々に調べる

集合へ変換すると重複が消えるため、集合の差だけでは重複行を見つけられない。次は実際に使った比較方法の説明用抜粋である。

```python
missing = set(listed_keys) - set(stored_keys)
extra = set(stored_keys) - set(listed_keys)
stored_duplicates = len(stored_keys) - len(set(stored_keys))
```

| 検査 | 意味 |
| --- | --- |
| `missing`が空 | 一覧で見た記事がDBにもある |
| `extra`が空 | DBに一覧外のIDが混ざっていない |
| `stored_duplicates`が0 | 保存行内に同じIDの重複がない |

### 再実行の副作用を確認する

新規保存が0であることに加え、詳細リクエスト数を確認した。一覧はチェックポイント照合のために必要だが、保存済み記事の詳細は再取得しなかった。

さらに対象外のメンバーについて、実行前後の件数、元のキー、DB IDに対応する状態を比較した。成功件数だけを見ると、別対象の状態を変えた処理を見落とし得る。

## つまずいたところ

運用上の件数確認のために一覧APIへ集計項目を追加したが、依頼範囲に不要だったため戻した。確認用途とAPI契約の分離については[件数確認のためにAPI契約を増やさない](./103-verify-counts-without-expanding-api.md)で扱う。

## 学んだこと

**INFERENCE:** 件数、集合、再実行時のリクエスト、対象外データの維持を組み合わせると、それぞれ異なる失敗を検出できる。どれか一つで全てを保証するものではない。

## 制約・次の課題

一致したのは「観測した一覧」と「保存したID」である。取得元の一覧自体に欠落がある場合や、本文が完全かどうかは別の検査が必要になる。取得期間中の一覧変更を一般的に排除できる仕組みまでは検証していない。
