# 長時間バックフィルを分割し、進捗カーソルから再開する設計

## 結論

数時間連続する初回バックフィルは、15〜30分程度の実行単位へ分割し、DBに保存した進捗カーソルから再開する方式へ変更するのが適切です。

この方式は本記事執筆時点では提案段階であり、実装済みではありません。

## 背景

現在の収集処理は、記事ごとにDBへ保存するため、途中で停止しても保存済みの記事は失われません。DBの一意制約によって重複保存も防げます。

しかし、ページ位置は保存していません。再実行すると先頭ページから調べ直し、保存済みの記事についても詳細ページへアクセスします。実際のバックフィルでは数時間を要し、記事数は4,348件から7,865件へ増えました。

## 解決したい課題

- PC再起動や通信失敗後に、先頭から再取得しない。
- 相手側へ数時間連続でアクセスしない。
- 失敗した区間だけを再実行できるようにする。
- バックフィル完了をDBから確認できるようにする。

## 前提・制約

- 記事単位の保存と重複防止は既存DBで実現済み。
- HTTPアクセスは並列化せず、設定した待ち時間を維持する。
- 通常の定期取得と初回バックフィルは別の実行モードとして扱う。
- 全件取得が完了するまでは、DBを完全なチェックポイントとして扱わない。

## 検討した選択肢

### Option A：1回のプロセスで最後まで取得する

#### メリット

- ジョブ状態を保存する追加実装が不要。
- 正常終了すれば1回で完了する。

#### デメリット

- 数時間にわたってアクセスが継続する。
- 中断後は先頭ページから確認し直す。
- 終了結果を後からDBだけで判定できない。

### Option B：時間またはページ数で分割し、進捗を保存する

#### メリット

- 実行時間とアクセス量に上限を設けられる。
- 中断後に続きから再開できる。
- 失敗区間と完了区間を区別できる。

#### デメリット

- ジョブ状態とカーソルのスキーマが必要。
- 一覧構造が変化した場合のカーソル無効化規則が必要。
- 完了判定と再試行状態の設計が増える。

## 評価軸

| 評価軸 | 連続実行 | 分割実行 |
| --- | --- | --- |
| 連続アクセス時間 | 数時間になる可能性 | 上限を設定可能 |
| 中断後の再取得 | 先頭から確認 | 保存位置から再開 |
| 実装量 | 少ない | ジョブ状態が必要 |
| 失敗区間の特定 | 実行ログに依存 | DBで保持可能 |
| 相手側への総アクセス削減 | 再実行時に不利 | 再取得を抑制可能 |

## 最終判断

今後のバックフィルは、時間またはページ数で分割し、取得元と一覧単位の進捗カーソルをDBへ保存する方針とします。

想定する最小状態は次のとおりです。

```text
source_key
archive_key
next_page
status
last_success_at
failure_count
```

## なぜこの選択をしたか

今回の実行では、記事の重複保存は防げても、HTTPアクセスの重複を防げませんでした。記事単位の一意制約とページ単位の進捗保存は別の責務です。

分割実行なら、1回15〜30分などの運用上限を設けながら、次回は保存済みページの続きから再開できます。初回取得が完了した後は、既存記事へ到達した時点で止める定期取得へ切り替えます。

## トレードオフ・今後の懸念

- ページの挿入や削除により、数値カーソルだけでは位置がずれる可能性がある。
- ページ番号に加えて、最後に確認した記事識別子や公開日時を保持する必要があるか検討する。
- `429`では`Retry-After`を尊重し、通常の再試行とは別に停止時間を扱う必要がある。
- 完了済みカーソルをいつ破棄するかは未決定。

## まとめ

重複保存を防ぐだけでは、長時間バックフィルの再取得コストは解消できません。実行時間を区切り、ページ進捗とジョブ状態を永続化することで、アクセス量・停止再開・失敗調査を管理可能にできます。
