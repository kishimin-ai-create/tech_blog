# エラー本文を公開せずに画像アップロードの失敗を区別する

## はじめに

画像生成APIの呼び出し側で、不正な入力画像と生成画像のサイズ超過を区別したい。一方、上流のエラー本文を利用者へそのまま公開せず、破棄する方針がある。MojicaとGlyph Forgeで、固定のレスポンスヘッダーを使ってこの2つを両立した。

## 前提・環境

- Mojica: ASP.NET Core API
- Glyph Forge: Python・FastAPIの画像生成サービス
- ローカル変更を両方接続して確認。本番への反映は未実施

## やってみた結果

`POST /images/frame-file`の422に、分類可能な場合だけ`X-Glyph-Forge-Error`を追加した。値は`INVALID_IMAGE`または`OUTPUT_SIZE_EXCEEDED`である。既存のステータスとJSON本文は維持し、それ以外の422にはヘッダーを必須としない。

Mojica側では既知のヘッダーを固定の公開エラーに変換し、ヘッダーがない場合や未知の値では共通の入力エラーを返す。上流本文は公開せず、期限付きで破棄先へ読み捨てる。

## 実装・検証

### ワーカーを越えて原因を伝える

画像生成は別プロセスで行う。入力画像の検証エラーと出力サイズ上限エラーを例外型で区別し、ワーカーから親プロセスへ種別を伝える。API層はframe-fileの対象エラーをヘッダーに写す。エラー文言を文字列比較して種類を推測しない。

### 古い上流にも対応する

Mojicaは認識できる値にだけ個別の案内を割り当てる。未知・欠落したコードを特定の画像エラーとして扱わず、互換性のある共通エラーへ落とす。サイズ超過には、元画像を小さくして再試行するよう日英で案内する。

### ローカルで確認する

変更中の両サービスをローカルで接続し、正常PNGは200、不正画像と出力サイズ超過はそれぞれ別コードの422になることを確認した。Mojicaのバックエンドテストは407件成功し、Glyph Forgeのテストは159件成功・5件スキップだった。

## つまずいたところ

元のMojica実装は上流の422をすべて出力サイズ超過として扱っていた。アップロードでは画像形式など別の理由でも422になるため、ステータスだけで分類できない。上流本文を読み込む方法も考えられるが、既存の本文を保持しない方針と衝突するため採用しなかった。

## 学んだこと

固定コードのヘッダーは、本文を上位へ渡さずに限定した分類を共有する方法になる。ただしヘッダーの意味と互換性を両サービスで維持し、旧版や未知の値への安全なフォールバックを用意する必要がある。

## まとめ

ローカル結合では2種類の失敗を区別できた。両変更はPRとしてレビュー中で、本番ではヘッダー対応版のGlyph Forgeへの切り替えが別途必要である。
