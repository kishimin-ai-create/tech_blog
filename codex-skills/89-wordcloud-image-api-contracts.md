# 画像APIの分離とimport時の実行を整理する

## はじめに

画像生成APIを通常生成とアップロード画像による生成へ分けた。この変更記録では、HTTP契約とモジュール配置を別々に扱い、古い実行方式のテストを置き換えた過程を説明する。

## 背景と目的

利用者は `/images/{entity_id}` と `/images/frame-file/{entity_id}` の2つを指定した。通常生成はGET、アップロード画像を使う生成はPOSTとし、後者の画像ファイルを必須入力にした。生成処理をリクエストから呼べるようにすることが目的だった。

## 実際にやったこと

FACT: 通常生成のテストと実装を `c87d66b`、`199e9a2` に、必須アップロードのテストと実装を `454cc9e`、`3853e0a` に分けた。根拠は対象リポジトリのGit履歴と `services/analysis/tests/test_image_routes.py` である。

| 契約 | 現在の定義 | 確認方法 |
| --- | --- | --- |
| 通常生成 | GET `/images/{entity_id}` | OpenAPIの操作登録とハンドラテスト |
| フレーム画像生成 | POST `/images/frame-file/{entity_id}` | OpenAPIの操作登録とハンドラテスト |
| 画像ファイル | 必須multipart入力 | requestBody.requiredの確認 |
| 応答 | PNGのFileResponse | モック化した生成処理の応答確認 |

FACT: `1b5d461` では旧来のimport時実行を前提にしたテストを削除し、ハンドラを呼んで生成と応答を確認するテストへ置き換えた。現在の `analyze.py` はルーターと処理を定義し、`main.py` がルーターを登録する。

ファイルを別々のルートモジュールに移した後、利用者の指示で `f227d9a` により両ハンドラを既存の `analyze.py` へ戻した。URLの分離は維持された。

## 実際の結果と検証

セッション内の最終実行記録は15テスト成功、全体カバレッジ96.71%。本記事作成時はコードとコミットを再確認し、アプリケーションのテストは再実行していない。テストは取得と生成をモック化しているため、実collectorとの接続や画像の見た目まで証明しない。

## 学んだこと

INFERENCE: HTTP操作の分離は、必ずしもファイルの分割を必要としない。公開契約をテストで確認し、配置変更は独立した判断として扱うと、要求されたAPIと既存構造を両立できる。

## 制約と次の課題

生成ファイルの応答後削除、外部取得のタイムアウト、実サービス接続の確認は残っている。通常のルート登録テストだけでそれらが解消したとは判断できない。
