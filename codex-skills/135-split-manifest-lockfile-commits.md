# package.jsonとlockfileが混在した変更を目的ごとにコミットする

## はじめに

devコマンド、ESLint、YAML整形、3種類のCIが同じ作業ツリーに混在していました。ユーザーから「1変更で1コミットが分かるように」と指示を受け、ファイル数ではなく、変更の目的と依存関係に合わせて分けました。

## 前提・環境

2026年10月21日、Windows、PowerShell、Bun 1.3.13を使ったblog-wordcloudの作業です。共有済み履歴の書き換えではなく、その時点の未公開変更を新しいコミットへ分けた記録です。

## やってみた結果

最初の整理を6コミットに分けました。

| コミット | 目的 |
| --- | --- |
| e2a33c9 | frontend/backendのdevコマンド統一 |
| f5c4845 | 共通ESLintの導入 |
| 2adfa5d | workflow YAML整形コマンド |
| 9e2b9bc | schemas CIの独立 |
| 45d2097 | backend検査とテストの分離 |
| 3ab3bc7 | frontend検査とブラウザテスト |

その後のStorybook専用script、独立build job、追加説明文書の削除も別コミットにしました。

## 実装・検証

### 共有ファイルの変更を目的へ対応させる

app/package.jsonとapp/bun.lockにはESLintとPrettierの両方の差分がありました。そのまま同じコミットへ入れると2つの目的が混ざります。

作業ツリーの退避を用意し、indexへESLint段階のmanifestとlockfileを構成しました。最終版の作業ファイルを保ちつつ、staged diffがその段階で必要な依存だけになるようにしました。

### 中間状態をインストールして確認する

staged manifestとlockfileを.git配下の確認用ディレクトリへ書き出し、そのappから `bun install --frozen-lockfile` を実行しました。ESLintだけを含む中間状態の依存インストールが成功したことを確認しています。

これは各コミットの全検証が成功したという意味ではありません。ソース上のLint違反やfrontend型エラーは別に残りました。

## つまずいたところ

ファイル単位で分けるだけでは、共通manifestとlockfileの目的を分離できませんでした。一方、lockfileだけを最終版のまま先にコミットすると、その時点のmanifestと対応するかを確認できません。

## 学んだこと

コミットの境界を作る際には、その時点で依存宣言とlockfileが対応することも検証対象になります。段階的な変更の説明には、最終作業ツリーの検査に加え、staged状態の検査が役立ちました。

## 根拠と制約

根拠は上記6コミットの差分、index構成時の退避、中間manifestのfrozen install結果です。これは手動整理の記録であり、汎用的なlockfile編集手順を保証するものではありません。今後は依存する順序で変更を実装・検証する方が、後から分割する作業を減らせるという提案です。
