# 実行時に組み立てる API の配線を PostgreSQL で確かめる

## 背景

API のリクエストテストでは、認証や保存処理をテスト用の関数へ差し替えていた。入力検証や HTTP 応答は確かめられるが、実際に使う DB アダプターが各ルートへ接続されているかは別の確認が必要だった。

## 対応

環境変数と共有 DB を使う API の組み立てを関数にまとめ、通常の起動でもテストでも同じ組み立てを使用する。テストでは一時的な管理者を作成し、その識別子に対応する認証情報でお気に入り、スキル、セクション別リンクの作成・更新・削除を API 経由で実行した。テストで作ったデータは識別子を使って後片付けする。

## 検証と結果

PostgreSQL を用いる Medium テストが GitHub Actions で成功し、[夜間 CI](https://github.com/kishimin-ai-create/profile-hub/actions/runs/41292031537) も全ジョブ成功した。それ以前の実行ではテスト自体は成功していたが、API の `index.ts` は関数カバレッジ 78.81% で閾値に届かなかった。

このテストが保証するのはテスト用 DB と設定での接続であり、本番環境のデプロイや同時更新時の振る舞いではない。ローカルでは PostgreSQL が利用できず、DB テストはスキップされた。

## 学び

依存関係を差し替えたテストと、実際の構成を通すテストは確認する境界が異なる。前者で異常系を細かく扱い、後者で認証から保存までの接続を検証すると、実行時の配線漏れを見つけやすくなる。カバレッジの数値だけでは配線の正しさは分からないため、レスポンスと DB の状態も確認する。
