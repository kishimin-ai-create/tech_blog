# JSONの取得経路を追加しても既存の通信制限を引き継ぐ

## はじめに

HTML中心の取得処理へJSONアーカイブの経路を追加した。別のAPIだからと無制限のHTTPクライアントを作るのではなく、既存の通信境界と解析処理を使う構成にした。

## 前提・環境

Python、HTTPX、Pydanticを使う。取得対象は非公開のローカル設定から注入する。実URL、フィールド名の対応、対象値は記事や公開テストへ載せない。

## やってみた結果

**FACT:** HTMLとJSONの取得が共通のテキスト取得処理を経由するようになった。JSONではメディアタイプの確認後にデコードし、壊れたJSONを取得失敗として扱う。実際の全件取得と再実行も完了した。

## 実装・検証

### 通信とデコードを分ける

既存クライアントは、HTTPS、許可ホストとポート、リダイレクト先、応答サイズ、期限を検査していた。テキストを読む部分を共通化し、HTMLとJSONで期待するメディアタイプだけを変えた。

次は実装の責務を示す説明用抜粋である。クライアント初期化などは省略している。

```python
def get_json(path):
    text = get_bounded_text(path, media_type="application/json")
    return validate_json(text)
```

JSON専用の呼び出し口を加えても、許可ホストを離れるリダイレクトを受け入れるようにはしていない。HTML取得の既存エラー表現も維持した。

### 記事解析の境界を引き継ぐ

アーカイブから受け取ったタイトル・日時・作者と本文を、既存の解析器が読む構造へ変換した。タイトルなどの文字列はエスケープし、本文HTMLは既存のサニタイズを通す。元の記事URLと記事IDの一致も検査する。

これはJSONを受け取っただけで本文を信頼する設計ではない。保存前には、本文の制限、画像ホストの許可、日時のタイムゾーンなども従来の解析境界へ渡す。

### リクエスト間隔と一時失敗を確認する

リクエストごとの待ち時間と一時失敗の再試行を既存処理から使った。テストでは一時的なHTTP失敗を返し、再試行と各要求の待機を確認した。実運用では並列化せず、設定済みの間隔で順番に取得した。

## つまずいたところ

今回確認された不具合は、表示名の引き継ぎ時点と、一覧の総ページ数の整合性だった。通信制限を共有しただけでは、このような業務上の整合性を保証できない。[総ページ数の検証](./101-zero-page-archive-contract.md)は別の契約として扱った。

## 学んだこと

**INFERENCE:** 応答形式が増えたときは、形式固有のデコードと、形式に依存しない通信制限を分けると境界を引き継ぎやすい。追加経路にも同じ制限が適用されることは、呼び出し経路と異常系テストで確認する必要がある。

## 制約・次の課題

許可ホストの設定自体の妥当性は運用側の責務として残る。既存の期限やサイズ上限を共有したという事実だけで、全ての外部応答や本文品質を検証済みとはしない。
