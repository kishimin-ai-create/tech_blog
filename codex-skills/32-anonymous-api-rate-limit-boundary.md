# 認証なしでMojica APIとGlyph Forgeのレート制限を分担する

## 結論

認証なしで利用者ごとの公平な制限を実現することはできない。Mojica APIからGlyph Forgeへ送る通信は、Glyph Forgeからは同じ送信元IPに見えるため、Glyph ForgeのIP制限を利用者制限として使うと、全利用者が一つのバケットを共有する。利用者向けの匿名制限はMojica APIまたはエッジで行い、Glyph Forgeは生成処理の容量保護を担当させるのが適切である。

## 背景

Mojica APIは画像生成リクエストをGlyph Forgeへ中継する。ブラウザの利用者A・B・Cが別々の端末から送信しても、Glyph ForgeへのTCP接続元はMojica APIのコンテナやプロキシになる。

```text
利用者A ─┐
利用者B ─┼→ Mojica API ─→ Glyph Forge
利用者C ─┘       送信元はAPI側に集約される
```

## 現在の制約

Mojica APIのレートリミッターは、現在の実装では固定キーでパーティションを作っている。

```csharp
RateLimitPartition.Get(
    ImageGenerationRateLimiterPolicy.PolicyName,
    _ => ImageGenerationRateLimiterPolicy.CreateLimiter(options));
```

このため、APIインスタンス内では全利用者が同じ制限を共有する。また、認証機構がないため、信頼できる利用者IDも存在しない。

## 検討した選択肢

### IP単位でMojica APIを制限する

認証なしで導入しやすい。一方、共有NAT配下の利用者が同一視されるため、厳密な利用者単位の公平性はない。

### 匿名Cookieをキーにする

個人情報やアカウントを保存せずに識別子を発行できる。ただし、Cookieの削除や別ブラウザで回避できるため、認証の代替にはならない。複数インスタンスでカウンターを共有するには、Redisなどの一時ストアも必要になる。

### Glyph Forgeへ利用者IDを転送する

Mojica APIが生成した識別子を渡すことはできるが、Glyph Forgeがその値を信頼するには、内部ネットワーク制限、サービス認証、または署名検証が必要になる。ブラウザから送られたヘッダーをそのまま転送してはいけない。

## 最終判断

認証なしを維持する場合は、利用者別制限ではなく匿名利用者向けの制限として次を採用する。

| 層 | 責務 |
| --- | --- |
| Mojica API / エッジ | IP単位のレート制限、429、`Retry-After` |
| Mojica API | 全体の同時実行数とキュー上限 |
| Glyph Forge | CPU・メモリ保護、画像生成の同時実行数、タイムアウト |
| ネットワーク境界 | Glyph Forgeの直接公開を防止 |

Glyph ForgeのIPレート制限を完全に削除するのではなく、内部専用なら利用者制限としては使わず、サービス全体を守る制限へ役割を限定する。

## トレードオフ・未解決事項

- 同一IPを共有する利用者は同じ制限を受ける。
- IPを変える利用者やCookieを削除する利用者を厳密には追跡できない。
- メモリ内カウンターは再起動・複数インスタンスで一貫しない。
- 1万人規模で公平な匿名制限が必要になった場合は、エッジの管理型レート制限またはTTL付きの一時ストアが必要になる。

## まとめ

認証なしでは「利用者」をサーバー側で確実に識別できない。したがって、Mojica APIまたはエッジで匿名アクセスを抑制し、Glyph Forgeでは送信元IPを利用者識別に使わず、生成サービス全体の容量を守る設計に分離する。
