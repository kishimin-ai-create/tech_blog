# 総ページ数0なのに記事がある応答を保存前に拒否する

## 結論

ページ数と記事配列の型が正しいだけでは、応答の整合性は保証できない。「総ページ数0かつ記事配列が非空」という矛盾を一覧の検証段階で拒否するよう修正した。

## 発生した問題

### 症状

総ページ数0の一覧に記事がある場合、その記事を保存して成功終了していた。ページ数は総ページ数であり、「現在のページ番号0」とは意味が異なる。

次は回帰テストの条件を簡略化した架空の応答である。

```json
{"pages": 0, "items": [{"id": 42}]}
```

### 発生条件

JSONの一覧APIをゼロ始まりのページ番号で走査するPythonの取得処理で発生した。最初の一覧を読む前は総ページ数を知らないため、0ページの応答でも初回リクエスト自体は必要になる。

### 影響

取得元が存在しないと報告したページの内容を、有効な取得結果として保存してしまう。

## 調査

### 件数の境界条件を回帰テストにする

既存の検証は、総ページ数が正なら空配列を拒否していた。その逆である「総ページ数0なら配列も空」を検査していなかった。

回帰テストでは、失敗数が1で保存数が0になることを要求した。修正前は失敗数0・保存数1となり、テストが失敗した。この失敗が実装の欠陥を再現する根拠となった。

## 原因

型や非負整数という単項目の条件と、ページ数・配列の対応関係という複数項目の条件を分けていなかった。

## 解決方法

記事配列を読み取る段階で、次の条件を追加した。これは実際の検証条件の抜粋である。

```python
if (
    not isinstance(items, list)
    or (count > 0 and not items)
    or (count == 0 and items)
):
    raise ParseContractError("archive record list is invalid")
```

一覧検証が失敗したら、詳細取得と保存へ進めない。失敗結果はコマンドの非ゼロ終了へつながる。

## 動作確認

| 応答 | 確認結果 |
| --- | --- |
| 総ページ数0・空配列 | 正常な空履歴として受け入れる |
| 総ページ数0・非空配列 | 一覧の失敗として拒否し、保存しない |
| 正の総ページ数・空配列 | 不完全な一覧として拒否する |

**FACT:** 修正後の全体テストは115件成功した。総ページ数の途中変更、同じ記事キー列のページ反復、最大ページ数到達を扱う既存ケースも通った。

## 再発防止

空の正常応答と、空に関係する矛盾した応答を別ケースとして保持する。値0を無条件に異常とする修正にはしない。

## 制約

ここで述べた条件は、空履歴が総ページ数0、各存在ページが非空配列を返す契約に対するものだ。空ページを許す別APIへそのまま適用するものではない。
