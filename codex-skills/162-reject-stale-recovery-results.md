# 復旧確認中の手動停止を、古い成功結果で解除しない

## 結論

非同期に進む復旧確認の結果は、確認開始時の`revision`が現在も一致する場合だけ反映する。確認中に利用者が再停止や手動再開を行った場合は、その操作を優先する。

slope-collectorで2026年10月24日に実装・検証した。対象は、外部通信の途中で別プロセスから管理操作が入る処理である。

## 背景と解決したい課題

自動再開の処理は、停止状態を読んでから外部サイトへ問い合わせる。通信中には、利用者が停止理由を変更したり、自動再開をやめて手動停止へ切り替えたりできる。

確認開始時の状態だけを見て成功結果を反映すると、「新しく停止したのに、以前の復旧確認が終わって解除された」という逆転が起こり得る。この例は競合として設計で扱ったもので、本番障害を観測したわけではない。

## 前提・制約

管理APIと復旧確認はDBを共有する別プロセスである。外部通信の間ずっとDBトランザクションを保持せず、確認後に最新の操作と整合する結果だけを反映したい。

## 検討した選択肢と評価軸

### Option A：確認結果をそのまま反映する

結果の適用処理は単純だが、確認中の手動操作を区別できない。

### Option B：対象のrevisionが一致する場合だけ反映する

操作・確認の識別子を保存する必要があるが、確認開始後に状態が置き換わったことを判別できる。今回はこの案を選んだ。

| 評価軸 | 無条件反映 | revision付き反映 |
| --- | --- | --- |
| 途中の手動操作の識別 | できない | 識別子の変更で判定 |
| 結果の更新条件 | 対象だけ | 対象・状態・revision |
| 保存する状態 | 少ない | revisionが必要 |

## 最終判断と実装

停止、再開、復旧確認の取得時に新しいrevisionを発行する。結果の適用は、対象、revision、停止中、自動再開モードという条件を含むDB更新で行う。構造を示すSQL相当の抜粋は次のとおり。

```sql
UPDATE collection_controls
SET paused = :paused, revision = :new_revision
WHERE target = :target
  AND revision = :claimed_revision
  AND paused = true
  AND resume_mode = 'automatic';
```

実際の実装はSQLAlchemyを使用し、確認時刻や次回予定も同じ更新へ含めている。更新件数が0なら古い結果として適用しない。このSQLは説明用であり、手動実行したものではない。

また、次の外部要求を送る前にも、確認開始時のrevisionが有効かを読み直す。新しい操作が入った場合、不要になった記事取得へ進まない。

## 実装後の結果

一覧応答中と記事応答中に、手動停止または手動再開を入れるテストを行った。いずれも新しい操作が残り、古い確認結果の適用件数は0だった。一覧応答中に変更したケースでは、記事への要求も行わなかった。

確認が成功しても、その後に通常収集を自動起動することはない。ここで守っているのは状態更新の整合性であり、収集の起動順序とは分けている。

## トレードオフ・今後の懸念

古い結果を捨てるため、利用可能な結果でも再確認が必要になる場合がある。テストはSQLiteとモックHTTPで行っており、実MySQLの競合実行は未検証である。

revisionは「この結果を今も適用してよいか」を判定するものだ。確認処理の通信が重なる問題には、別途、実行時間を考慮した予約が必要になる。
