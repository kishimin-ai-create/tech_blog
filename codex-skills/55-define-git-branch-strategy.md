# 小さな開発でもレビュー可能にするGitブランチ戦略を文書化する

ドキュメントだけの変更でも、どのブランチから始め、どの条件で`main`へ統合するかが曖昧だと、レビュー範囲と依存関係を後から確認しにくくなります。本記事では、slope-collectorの`docs/branch-design.md`に記録したブランチ命名、Pull Request、検証、MVPの依存関係を整理します。

## 結論

- 1つの変更目的を1つの作業ブランチと1つのPull Requestへ対応させる。
- ブランチ名は`{type}/{issue-number}-{short-description}`とし、ブランチの種類とコミット種別を分ける。
- `main`への反映はPull Requestのマージだけに限定し、緊急時も通常経路を使う。
- 依存する作業は前提となるPull Requestのマージ後に始め、独立したAPIと収集処理は並行開発できる。
- Rulesetとローカルhookの役割を分け、サーバー側の保護を最終的な強制境界とする。

## 文書化した対象

今回追加した文書は、コードの振る舞いではなく、slope-collectorの開発作業を統合する規則を扱います。確認できる変更は次の1ファイルです。

```text
docs/branch-design.md
```

この文書は、作業ブランチ`docs/define-git-branch-strategy`上のコミット`1a36097`で追加されています。したがって、文書の追加コミットが存在することと、その内容が`main`へ統合済みであることは別に扱う必要があります。

## ブランチ名とコミット種別を分ける

ブランチの種類は変更の責務を表します。

| 種類 | 用途 |
| --- | --- |
| `feature/` | 利用者向けまたはドメインの振る舞い |
| `fix/` | 不具合修正 |
| `refactor/` | 振る舞いを変えない構造改善 |
| `docs/` | 文書だけの変更 |
| `test/` | テストだけの変更 |
| `chore/` | ツール、依存関係、マイグレーションなどの保守 |

`feat/`はブランチ名には使わず、振る舞いを追加するConventional Commitsの種別として予約します。これにより、ブランチ名は作業のまとまりを、コミット種別は履歴上の変更内容を表せます。

## Pull Requestまでの流れを固定する

文書では、依存関係の確認から作業ブランチの削除までを次の順序で定めています。

1. 依存するIssueが`main`へ統合済みであることを確認する。
2. ローカルの`main`をリモートの`main`へ更新する。
3. 更新済みの`main`から作業ブランチを作成する。
4. 選択したIssueの受け入れ条件だけを実装する。
5. リポジトリに定義された整形、型チェックまたはコンパイル、Lint、テスト、カバレッジを実行する。
6. `main`を対象にPull Requestを開く。
7. 必須チェックとレビューが成功した後にマージする。
8. マージ済みの作業ブランチを削除する。

依存する作業は前提のPull Requestがマージされるまで開始しません。長期間の積み上げブランチを使わないため、各Pull Requestを現在の`main`との差分としてレビューできます。

## MVPの依存関係を先に表にする

MVPの計画では、データベース接続、モデル、マイグレーションを先に統合し、その後に読み取り専用APIと収集処理を分けます。APIと収集処理は共通の前提が統合された後は互いに依存しないため、並行開発が可能です。

一方、収集処理の信頼性改善は収集処理の後、日次収集の設定は信頼性改善の後に置かれています。最後のエンドツーエンドテストとデプロイ検証は、両方の経路が統合された後に始めます。

これは単なる作業順の一覧ではありません。各作業の開始条件を明示することで、未統合の前提に依存したブランチを作らないための判断材料になります。

## `main`の保護を二段階で考える

文書では、GitHubのRulesetに次の条件を求めています。

- Pull Request経由の更新を必須にする。
- 必須status checkが導入された後は、それらを必須にする。
- force pushとブランチ削除を禁止する。
- 通常運用の迂回経路を用意しない。

ローカルの`pre-push` hookは、誤った送信先を早く検出する補助策です。最終的な強制境界はサーバー側に置きます。

今回の作業では、Rulesetは`main`へ先に追加済みです。一方、`docs/branch-design.md`そのものは作業ブランチにある未マージのコミットです。Rulesetが有効であることを、文書コミットが統合済みであることの根拠にはしません。

## 対象外と制約

この文書は、実装コードや受け入れ条件の内容を定義しません。各Issueの詳細な仕様、実際のCIで使うstatus check名、緊急時にRulesetを変更する権限と復旧手順も、文書の範囲では確定していません。

また、取得対象を特定できるURL、selector、識別子、クラス名、対象固有のfixture、秘密情報、`.env`ファイルはコミットしない規則です。ブランチ戦略の文書化によって、取得対象の公開範囲や取得許可が決まるわけではありません。

## 検証

今回確認したのは、文書の差分とGit履歴です。

```powershell
git log --oneline -- docs/branch-design.md
git diff 1a36097^ 1a36097 -- docs/branch-design.md
```

コミット`1a36097`では`docs/branch-design.md`だけが追加され、100行の文書差分になっています。これは文書内容の確認結果であり、MVPの実装、CIの必須チェック、全Issueの完了を示す検証ではありません。

## 学び

ブランチ名、Pull Requestの統合条件、依存関係、共有ブランチ保護を1つの文書へまとめると、作業開始条件とレビュー対象を同じ基準で確認できます。ただし、文書化は運用の説明であり、サーバー側のRulesetや各Pull Requestのチェック結果を置き換えません。

今回の変更は、ブランチ戦略を追加した未マージの文書コミットです。Rulesetの先行設定と文書の統合状態を分けて確認することが、公開済みの保護と作業中の提案を混同しないためのポイントになります。
