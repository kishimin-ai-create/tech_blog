# ImageGenerationFormの統合テストをSmallから設計する

## 結論

Mojicaでは、ImageGenerationFormの主要な画面状態とAPIエラーを、実ネットワークを使わないMSW境界のSmallテストとして先に列挙した。入力、クライアント検証、422のフィールドエラー、400・429・500・502・504のフォームエラー、Retry-After、成功時のPNGダウンロードを、ユーザーが観測できる振る舞いとして14ケースに分けている。

## なぜ先にテストケースを設計するのか

フォームは入力部品、React Hook Form、APIミューテーション、i18n、エラー表示、ダウンロードを組み合わせる。実装から始めると、エラー種別や再試行条件が抜けやすい。そのため`ImageGenerationForm.small.test.tsx`では`describe`を初期表示、送信、API検証エラー、APIエラーバナー、再試行、成功に分け、未実装ケースを`test.todo`として固定した。

## Smallとした根拠

MSWで`POST /images`をプロセス内でインターセプトし、実サービス、実ネットワーク、実データベースを使わずにフォームからAPI境界までを検証する。したがって、実ネットワークを必要とするMediumではなくSmallに分類した。

## 設計した観測点

| 領域 | 観測する振る舞い |
| --- | --- |
| 初期表示 | 日本語／英語のラベル、空の入力、標準画像タイプ、生成操作 |
| 送信 | 有効値のPOST、二重送信防止、クライアント検証による送信阻止 |
| 422 | `errors[].field`を該当入力へ表示し、アクセシブルに関連付ける |
| 400〜504 | エラー種別ごとのフォームレベルメッセージと内部詳細の非表示 |
| 429 | `Retry-After`中の再送不可、期限後の再送、ヘッダーなしの即時再送 |
| 成功 | PNGをレスポンスのファイル名で自動ダウンロードし、プレビューを描画しない |

## 検証

テストファイルを追加後、対象テストを実行し、14件がtodoとして認識されることを確認した。これは実装完了を示すものではなく、後続のGreenフェーズで一件ずつ実装するための契約である。

## まとめ

統合フォームのテストは、APIのステータスコードを並べるだけでなく、利用者が見るメッセージ、操作可能性、アクセシビリティ、ダウンロード結果へ変換して設計する。実ネットワークを使わないMSW境界なら、Smallテストとして高速な回帰確認を先に用意できる。
