# Content-Lengthのない画像アップロードでサイズ上限を適用する

## 結論

画像アップロードの実サーバー結合確認で、上限を超える分割送信が日本語の413ではなく英語の400になった。Content-Lengthがないリクエストをフォーム解析前に上限付きで読み、超過をAPIの413へ変換するようにした。正常な分割送信もローカルで200 PNGになることを確認した。

## 発生した問題

Mojicaの画像アップロードAPIでは、リクエスト全体を2 MiBと64 KiBのフォーム領域に制限する。Content-Lengthのある超過リクエストを確認した後、実サーバーへContent-Lengthのないmultipartリクエストを分割送信したところ、次の結果になった。

```text
期待: 413 と日本語のサイズ上限エラー
実際: 400 と英語のフォーム解析エラー
```

ASP.NET Coreのテスト用サーバーでの確認だけでは、この実サーバーの振る舞いを再現できなかった。

## 調査

Content-Lengthが指定された場合は、フォーム解析の前に全体サイズを確認できる。一方、長さが指定されていない場合は本文を受信して初めて実際のサイズが分かる。修正前はKestrelの読み取り上限に到達した例外がフォーム解析時に発生し、API固有の413へ変換されず、400の応答になった。

## 解決方法

対象エンドポイントのリソースフィルターで、長さがない本文をフォーム解析前に上限付きで読み取る。上限を超えた場合と、読み取り中にサーバー側の上限例外が発生した場合は、利用者の言語に応じた`REQUEST_TOO_LARGE`を413で返す。制限内ならバッファを巻き戻して後続のフォーム解析へ渡す。本文のバッファリングは上限内に制限し、キャンセルを受け付ける。

これはHTTPリクエスト全体の保護であり、画像形式・画像寸法・デコード安全性の検証は上流の画像生成サービスが担当する。

## 動作確認

変更中のMojica APIとGlyph Forgeをローカルで起動し、以下を確認した。

| 入力 | 結果 |
| --- | --- |
| 通常の有効画像 | 200、PNG |
| 不正画像 | 422、`INVALID_IMAGE` |
| 出力サイズ超過 | 422、`IMAGE_OUTPUT_SIZE_EXCEEDED` |
| 有効な分割送信 | 200、PNG |
| 上限超過の分割送信 | 413、`REQUEST_TOO_LARGE`と日本語メッセージ |

Mojicaのバックエンドテストは407件成功し、行カバレッジ93.94%、分岐カバレッジ93.79%だった。検証はローカル環境であり、本番のリバースプロキシを含む経路は未確認。

## 再発防止

長さ付き・長さなしの双方について上限を確認するテストを追加した。実際の分割送信もローカルの結合確認で試した。ホスティング環境固有のリクエスト制限と競合する可能性は、デプロイ後に確認が必要である。

## まとめ

Content-Lengthのチェックだけで実際の受信量は判断できない。分割送信はフォーム解析前の境界と実サーバーの両方で確認する。
