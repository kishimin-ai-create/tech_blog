# JWTの失効判定をセッションバージョンとDB照合に分ける

署名が正しく期限内のJWTでも、ログアウト後は拒否したい。profile-hubでは、そのための準備をDBの状態、トークンの照合、DB検索の3つに分けて実装した。この記事の対象は部品の検証までであり、ログインやログアウトの完成ではない。

## バージョンを永続化する

[PR #80](https://github.com/kishimin-ai-create/profile-hub/pull/80) は管理者の `session_version` を追加する。初期値は0で、DB制約により負の値を拒否する。マイグレーションを適用したPostgreSQLで、初期値、増加、負値の拒否を確認した。

バージョンをDBに置くのは、複数のAPIインスタンスが同じ失効状態を参照できるようにするためだ。ただし列を追加しただけでは、既存のトークンは失効しない。

## 署名と現在値を照合する

[PR #81](https://github.com/kishimin-ai-create/profile-hub/pull/81) では、署名・期限・種別などを検証した後で、トークン内のバージョンを現在値と照合する。管理者が存在しない場合や値が異なる場合は認証結果を返さない。無効なトークンはDB検索より先に拒否される。

[PR #82](https://github.com/kishimin-ai-create/profile-hub/pull/82) は管理者IDから現在のバージョンを取得する。PostgreSQLを使うテストでは、作成直後の0、更新後の1、削除後の不在を確認した。

## 検証した範囲

BunのAPIテストは専用PostgreSQLを使い54件成功した。APIの整形、型チェック、Lintも成功した。PR #80〜#82のPostgreSQL integration CIはそれぞれ成功している。これらのPRは執筆時点で未マージである。

今回の部品はHTTPルートに接続されていない。ログアウト時のバージョン更新、並行リクエストの扱い、リフレッシュトークンの運用、試行制限、認証情報の保存方式は別途実装・検証が必要である。特に署名済みのトークンを持つことと、現在も認可されていることは別の判定になる。

署名と必須クレームの検証については、[JWTの必須クレーム検証と失効管理を分けて考える](./189-jwt-required-claims-versus-revocation.md)を参照する。
