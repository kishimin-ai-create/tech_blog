# ランダム郵便番号APIで「CSVの行」ではなく「一意な郵便番号」を抽選する理由

## 結論

日本郵便のCSVからランダムな郵便番号を返すAPIでは、元CSVの行を直接抽選せず、同じ郵便番号の住所をまとめた後の「一意な郵便番号」を抽選単位にする。

```ts
type PostalCode = {
  postalCode: string;
  addresses: [Address, ...Address[]];
};
```

この設計により、元データで複数行を持つ郵便番号だけが高確率で選ばれる偏りを避けながら、同じ郵便番号に対応する住所を欠落なく返せる。

## 背景

Zipnamiは、日本郵便の公開データから郵便番号をランダムに1件返すWeb・Android向けアプリとして設計した。

ここで注意が必要なのは、7桁の郵便番号とCSVの1行が必ずしも1対1ではないことである。同じ郵便番号に複数の住所レコードが対応する場合、行をそのまま抽選すると、その郵便番号は行数の分だけ抽選候補へ重複して入る。

## 解決したい課題

次の2つを同時に満たす必要があった。

1. 各郵便番号を同じ確率で選ぶ。
2. 選ばれた郵便番号に対応する住所をすべて返す。

住所を1件に潰すと情報が欠落する。一方、CSV行をそのまま残して抽選すると確率が偏る。表示の都合と抽選の都合を同じデータ単位へ押し込めないことが重要だった。

## 前提・制約

- 抽選対象は日本全国の一意な7桁郵便番号である。
- 同じ郵便番号の全住所を保持する。
- `prefecture`、`city`、`town`が完全一致する住所だけを重複除去する。
- 住所順は元データの初出順を維持する。
- 実行時に日本郵便や別の住所APIへ問い合わせない。
- Androidへ全郵便番号データを同梱しない。

## 検討した選択肢

### Option A: CSVの行を直接抽選する

実装は単純だが、同じ郵便番号が複数行に存在すると選択確率が上がる。また、APIが1行だけ返す設計では、同じ郵便番号の別住所を失う。

### Option B: 一意な郵便番号へ正規化してから抽選する

ビルド時に郵便番号でgroupingし、住所を配列へまとめる。実行時は正規化済み配列のindexを一様に選ぶ。

```ts
const index = getUniformInteger(0, postalCodes.length);
return postalCodes[index];
```

正規化処理は増えるが、抽選確率と住所保持の契約を分離できる。

## 評価軸

| 評価軸 | CSV行を直接抽選 | 一意な郵便番号を抽選 |
| --- | --- | --- |
| 郵便番号ごとの確率 | 行数に影響される | 同じ確率にできる |
| 複数住所 | 欠落または重複しやすい | 配列で全件保持できる |
| Runtime処理 | 単純 | 正規化済みなら単純 |
| Build時処理 | 不要 | groupingと検証が必要 |

## 最終判断

一意な郵便番号を抽選単位とし、住所を`addresses`の非空配列として保持する設計を採用した。APIの`GET /api/random`は、正規化済みcollectionの件数を上限として1 indexを選ぶ。

## なぜこの選択をしたか

製品が利用者へ提示する「ランダムな郵便番号」は、元CSVの「ランダムな行」と同じ意味ではない。利用者から観測できる対象に確率を合わせる必要がある。

また、正規化をビルド時へ寄せることで、Cloudflare Workerのrequest処理はデータ読込とindex抽選へ限定できる。Runtimeで外部APIや複雑なgroupingを行わない境界も維持できる。

## トレードオフ・今後の懸念

- ビルド時正規化の決定性と重複除去をテストする必要がある。
- 一様性を統計テストだけで証明することはできない。先頭・末尾indexの境界と抽選関数への入力を決定的に検証する必要がある。
- 生成物形式とWorkerのサイズ制約は実装時に確定する。
- 日本郵便データ更新時に正規化結果のdriftを検出する仕組みが必要になる。

## まとめ

ランダム抽選の単位は、データソースの行ではなく、利用者が認識するdomain objectへ合わせる。郵便番号ごとの確率を公平にしながら複数住所を保持するには、ビルド時に一意な郵便番号へ正規化し、`addresses`配列を持つ単位から抽選する設計が適している。
