# 開発用収集データをローカルDBだけに保存する境界をADRで固定する

開発用の収集データをどこへ保存し、誰が見られるようにするかは、コードだけでは復元しにくい設計判断です。本記事では、開発PCのローカルDBへ保存し、DBと確認経路をそのPCだけに限定する方針をADRへ記録した理由を整理します。

## Decision

開発用の収集データは開発PC上のローカルDBへ保存し、DBと確認APIはローカルアドレスからのみ到達できる境界に置きます。本番や共有環境の保存方針は、この判断の対象外です。

## なぜコードだけでは不十分か

Composeのポート設定や環境変数を見れば、現在の接続先は分かります。しかし、なぜ外部公開しないのか、共有DBを採用しなかったのか、将来の変更で守るべき条件はコードだけでは分かりません。

ADR-0064では、次の判断を分離して記録しました。

- 保存先は開発PC上のDBに限定する。
- DBポートと確認APIもローカルアドレスに限定する。
- 開発環境の設定を共有環境や本番環境へ流用しない。

## 代替案との比較

共有DBへ保存すれば複数端末から同じデータを見られます。一方で、今回の「このPCだけ見られる」という要件を満たしません。

DBはローカルのまま確認APIだけを外部公開する案もありますが、API経由で開発データを外部から参照できるため、保存境界と閲覧境界が一致しません。そこでDBだけでなく確認経路もローカルに限定しました。

## 実装と検証

ADRの判断に対応する構成は、開発用Compose設定、DB接続設定、開発用確認APIに分かれています。確認時点のDBはローカルポートで稼働し、テーブル件数は次のとおりでした。

| テーブル | 件数 |
| --- | ---: |
| entities | 60 |
| records | 4,348 |
| assets | 23,677 |

この件数は全件バックフィル完了を示しません。外部応答待ちが長く、全件取得の終了結果は未確認です。ADRが保証するのは保存・到達範囲であり、収集件数の完全性ではありません。

## 将来の判断基準

開発データを別環境から参照したくなった場合は、既存設定を広げるのではなく、新しいADRで保存範囲・認証・公開範囲を改めて決めます。開発DBを外部アドレスへ公開する変更や、外部から確認APIを利用できる変更は、このADRに反します。
