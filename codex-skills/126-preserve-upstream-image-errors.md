# 画像APIのプロキシで上流のエラーを200 PNGにしない

## 結論

上流のHTTPステータスを確認せず画像として返すと、上流のJSONエラーまで`200 image/png`として返してしまう。`response.ok`を先に確認し、失敗時は画像の成功経路へ進めないようにした。

## 発生した問題

画像ルートは、上流レスポンスを無条件に`arrayBuffer()`で読み、HTTP 200と`image/png`を付けていた。解析サービスが422や500を返しても、バッファとしては読めるため、そのまま成功扱いになる。

レビューでは、画像デコードの失敗や監視上の成功扱いにつながる点が指摘された。これらはコードから予想される影響であり、本番で観測した障害ではない。

## 調査

対象は`app/backend/src/routes/images/images.ts`。旧実装に成功判定がないことを確認し、ユーザーの追加した分岐を確認した。

## 解決方法

コミット`d5f6a04`の変更は次のとおり。

```ts
if (!response.ok) {
  switch (response.status) {
    case 422:
      return c.json({ message: await response.text() }, 422);
    default:
      return c.json({ message: await response.text() }, 500);
  }
}
```

成功時だけ後続の画像読み込みへ進む。すべての上流ステータスを透過する実装ではなく、422は維持し、その他の失敗は500へ変換する。

## 動作確認

上流fetchをモックへ置き換え、Honoの`app.request()`で確認した。

| 上流 | 返却ステータス | 返却形式 |
| --- | --- | --- |
| 200 | 200 | image/png |
| 422 | 422 | application/json |
| 500 | 500 | application/json |
| 503 | 500 | application/json |

失敗ケースでは`message`にモックの本文が入ることも確認した。実APIへの接続と画像デコーダーによる確認は実施していない。

## 再発防止と制約

今回は一時的なモック検証であり、コミット済みの回帰テストはhealthの1件だけである。提案として、この表の分岐を永続的なテストへ移す。

また、422のOpenAPI定義、例外時のerror/message不整合、上流本文の情報公開範囲、本文のサイズ上限は別途検討が必要である。

## まとめ

HTTPの通信結果と、受信本文をバッファとして読めることは別である。画像のContent-Typeを付ける前に、成功と失敗の契約を分ける。

## 根拠

blog-wordcloudのコミット`d5f6a04`と、2026年10月18日の200・422・500・503のモック検証。執筆時点で同コミットはローカルにあり、PRのheadは直前の`a001770`だった。
