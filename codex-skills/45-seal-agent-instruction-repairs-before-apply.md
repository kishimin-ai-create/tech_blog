# AIエージェントの指示修復で、候補を封印してから適用する理由

## 結論

失敗セッションを根拠にSkillやAgent定義を直すときは、実ファイルを直接編集せず、隔離した候補を検証してrevisionを確定し、その同じrevisionへの明示承認後だけ適用する設計を採用した。

この設計で重要なのは、レビュー画面を用意することだけではない。レビューした候補と実際に適用する候補が同一であること、検証後に元ファイルや候補が変わっていないこと、部分失敗から戻せることを機械的に確認する点にある。

## 背景

失敗したAIエージェントのセッションには、ユーザーの訂正、ツール結果、使用したSkillなど、指示改善の根拠が残る。一方で、テストが通った候補をそのまま実ファイルへ反映すると、次の境界が曖昧になる。

- ユーザーが確認した差分と、適用時の差分が同じか。
- 検証後に候補が差し替えられていないか。
- 修復中に別の編集が入っていないか。
- 複数ファイルの途中で失敗した場合に元へ戻せるか。
- セッション本文やサンプル出力をいつまで保持するか。

今回作成した`repair-session`は、MITライセンスの[agent-repair](https://github.com/tankadoko/agent-repair)を参照し、CodexとClaude Codeの両方を扱えるようにした。適用方針は、プレビュー指定がない限り進める方式ではなく、毎回ユーザーの明示承認を要求する方式へ変更した。

## 解決したい課題

修復ワークフローには、診断の正しさと変更操作の安全性という2種類の課題がある。

診断では、元の失敗だけを偶然通す修正では不十分である。別入力と既存挙動も確認し、修復が一般化できることを示す必要がある。

変更操作では、「確認済みの候補だけを適用する」という約束を、会話上の注意だけに依存させたくない。候補、結果、実ファイルをハッシュとrevisionで結び付け、適用直前にも不変条件を検査する必要がある。

## 前提・制約

- セッション本文には機密情報が含まれる可能性がある。
- 投稿、購入、デプロイなどの外部副作用をテストとして再実行できない。
- Skill本体だけでなく、補助スクリプトやAgent定義も同時に修復する場合がある。
- 修復候補のテスト中に、実ファイルを変更してはならない。
- 適用後にユーザーが加えた編集を、ロールバックで上書きしてはならない。

## 検討した選択肢

### Option A：実ファイルを直接編集する

#### メリット

- 手順が短い。
- 通常の編集・テストツールをそのまま使える。

#### デメリット

- before／after比較中に元の状態が失われる。
- テストした内容と適用済み内容の同一性を示しにくい。
- 部分失敗とロールバックの境界が曖昧になる。

### Option B：差分を表示してから手動コピーする

#### メリット

- ユーザーが適用前に内容を確認できる。
- 専用の適用機構がなくても運用できる。

#### デメリット

- レビュー後に候補が変わっても検出できない。
- コピー先がステージ時点から変わっていても上書きし得る。
- 複数ファイルの途中失敗を復旧しにくい。

### Option C：候補を隔離し、封印済みrevisionを承認する

#### メリット

- 元ファイル、候補、テスト結果を同じrevisionへ結び付けられる。
- 適用直前の変更競合を検出できる。
- ロールバック用の元ファイルを保持できる。

#### デメリット

- stage、seal、results、applyという追加手順が必要になる。
- 外部Automationのようにファイルではない対象は、別の更新ツールと確認手順が必要になる。

## 評価軸

| 評価軸 | 直接編集 | 差分後に手動コピー | 封印済みrevision |
| --- | --- | --- | --- |
| レビュー対象と適用対象の同一性 | 低い | 中程度 | 高い |
| 競合検出 | 低い | 運用依存 | ハッシュで検出 |
| 部分失敗からの復旧 | 難しい | 難しい | 元コピーから復旧 |
| 手順の短さ | 短い | 中程度 | 長い |
| 機密データの保持制御 | 運用依存 | 運用依存 | 完了処理へ組み込み可能 |

## 最終判断

Option Cを採用した。ケースディレクトリに元ファイルと候補を分離して保存し、候補を封印するとrevisionと差分を生成する。テスト結果は、そのrevisionをレビュー済みであること、各確認項目のbefore／after、証跡を持つ。

適用時には、ユーザーが承認したrevisionを明示する。

```text
python <skill-dir>/scripts/repair.py apply <case> \
  --results <results.json> \
  --approved-revision <sealed-revision>
```

PowerShellでは行継続記号が異なるため、実行環境に合わせて1行で指定するかバッククォートを使う。

テスト計画では、最低でも次の3種類を区別する。

```json
[
  {"name":"original-failure","kind":"source","check":"元の失敗が解消する"},
  {"name":"different-input","kind":"similar","check":"別入力でも判断できる"},
  {"name":"preserved-behavior","kind":"regression","check":"既存挙動を維持する"}
]
```

適用直前には、元ファイルと候補のSHA-256がステージ・封印時から変わっていないことを検査する。適用成功後は`session.json`と`samples/`を削除し、検証結果とロールバック資産を残す。

## なぜこの選択をしたか

レビュー済み差分を表示するだけでは、Time of CheckとTime of Useの間に候補が変わる可能性が残る。revisionとファイルハッシュを使うと、レビュー、テスト、適用を同じ候補へ固定できる。

また、適用処理は複数ファイルを順番に書き換える。途中で失敗した場合、すでに変更したファイルを元コピーから復元する。ロールバック時に実ファイルが適用直後のハッシュと異なれば、後続編集が存在すると判断して上書きしない。

## 実装後の結果

Windows 11、Python 3.12.4で8件のUnit Testを実行し、すべて成功した。`repair.py`のstatement・branch込みカバレッジは85%だった。

確認した振る舞いには、次が含まれる。

- 承認なしの適用拒否
- ステージ後に変更された元ファイルの拒否
- 資格情報ファイルとケース外パスの拒否
- 複数ファイル適用中の部分失敗からの復元
- 適用後に入った編集をロールバックで上書きしないこと
- 適用成功後のセッション本文とサンプル出力の削除

Automationまたは定期タスクの実環境更新は対象がなかったため、実施していない。外部対象では、製品が提供する更新ツールでプロンプトだけを変更し、更新直前と直後に設定を読み直す手順をSkill側で定義した。

## トレードオフ・今後の懸念

- revisionを引数へ渡すだけでは、人間が承認した事実そのものを暗号学的に証明できない。Skillの「差分を提示して停止する」手順と組み合わせる必要がある。
- セッション形式が変われば、診断根拠の抽出処理も更新が必要になる。
- 完了前のケースには会話本文が残るため、ケース保存先のアクセス境界を維持する必要がある。
- 85%は未実行分岐が残ることを意味する。新しい障害を観測したときは、再現テストを先に追加する。

## まとめ

AIエージェントの指示修復では、正しい文章を書くことだけでなく、「どの候補を、何で検証し、誰が承認し、何を適用したか」をつなぐ必要がある。

候補の隔離、revisionによる封印、before／after結果、適用直前のハッシュ検査、競合を尊重するロールバックを組み合わせると、修復作業を再現可能な変更手順として扱える。
