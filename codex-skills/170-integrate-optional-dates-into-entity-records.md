# 著者ごとの全件取得へ日付条件を統合し、片側だけの指定も受け付ける

## 結論

対象読者は、既存の全件取得APIへ期間の絞り込みを追加する開発者である。slope-collectorでは、`GET /entities/{entity_id}/records`に`from`と`to`をそれぞれ任意の条件として追加した。日付なしならその著者の全件、片側だけならその側だけを制限し、両方あれば指定期間の全件を返す。

この記事は2026年10月24日の設計変更を扱う。変更はPR #43へ公開しており、記事執筆時点では未マージである。[先に追加した専用API](./167-complete-date-range-api-without-changing-pagination.md)は、その後の利用者の選択により撤去した。以前の設計が現在も有効であるかのようには扱わない。

## 背景

最初の要望は「日付範囲内の記事を件数で打ち切らずに取得したい」だった。その段階では、ページ分割する`/records`とは別に、両端の日付を必須とする`/records/by-date`を追加した。

その後、日付を指定しない場合の扱いを確認した際、利用者は「今ある全件取得に日付範囲指定を統合する」方針を選んだ。統合先は著者ごとの全件取得APIとなり、さらに`from`だけ、`to`だけの指定も要件に加わった。

## 解決したい課題と制約

必要だったのは、全件取得の入口を増やし続けることより、既存の著者単位の読み取りへ任意の条件を加えることだった。

- 著者を指定するパスと、既存の`id`・`title`・`body`の応答を維持する。
- 日付の有無によって著者の絞り込みを外さない。
- 日付は日本の暦日として解釈する。保存済み時刻はUTCのまま扱う。
- 既存の`/records`のページ分割とUTCによる日付条件は変更しない。
- 開発用のローカル確認APIという公開範囲を維持する。

全件とは、DBに保存された該当記事の全件である。外部サイトから不足分を取得する処理は起動しない。

## 検討した選択肢

| 評価軸 | 専用の日付範囲APIを維持 | 既存の著者別全件取得へ統合 |
| --- | --- | --- |
| 日付なしの取得 | 専用APIでは日付が必須 | 既存どおり著者の全件 |
| 著者の指定 | 任意のクエリ条件 | パスによる必須条件 |
| 応答の項目 | 日付範囲APIの項目 | 既存の`id`・`title`・`body` |
| 全件取得の入口 | 専用の入口が増える | 既存の入口へ集約 |

利用者が後者を選んだため、専用ルートとその応答モデルを削除し、既存ルートへ独立した任意条件を追加した。全著者をまとめて日付範囲で返す専用APIの機能は、この統合後には提供しない。

## 実装した契約

次の例の`1`は説明用の著者IDであり、実データではない。

| 呼び出し | 取得対象 |
| --- | --- |
| `/entities/1/records` | 著者の保存済み記事すべて |
| `/entities/1/records?from=2026-10-01` | 日本時間の10月1日00:00以降 |
| `/entities/1/records?to=2026-10-07` | 日本時間の10月7日の終わりまで |
| `/entities/1/records?from=2026-10-01&to=2026-10-07` | 日本時間の両端の日を含む期間内 |

クエリはまず著者条件と並び順を作り、その後に指定された日付条件だけを追加する。次は実装の構造を示す抜粋で、`start`と`end`は指定された日本の日付からUTCへ変換した時刻である。

```python
statement = (
    select(Record)
    .where(Record.entity_id == entity_id)
    .order_by(Record.published_at.desc(), Record.id.desc())
)
if from_date is not None:
    statement = statement.where(Record.published_at >= start)
if to_date is not None:
    statement = statement.where(Record.published_at <= end)
```

この構造なら、日付がなくても著者条件は残る。省略した側の日時を仮の最小値や最大値で埋める必要もない。日本時間とUTCの変換境界は[既存記事168](./168-japanese-calendar-dates-and-utc-query-bounds.md)、表現範囲外の開始日は[記事169](./169-timezone-conversion-datetime-limits.md)で扱う。

存在しない著者は`404`、存在する著者に該当記事がなければ`200`と空の`records`配列を返す。取得対象として非アクティブになった著者についても、保存済み記事は読み取れる。

## 実装後の結果

HTTP契約を先に変更した段階では、対象24ケースのうち17件が失敗し、7件が成功した。実装後は24ケースすべてが成功した。以下はそのテストで確認した事項である。

- 日付なし、開始日のみ、終了日のみ、両端ありの取得。
- 日本時間の境界と年の変わり目、100件を超える一致記事の全IDと順序。
- 著者の分離、非アクティブな著者、未知の著者と空の著者の区別。
- 不正な日付、逆転した範囲、UTCで表現できない開始日のエラー。
- OpenAPIからの旧ルート削除と、`from`・`to`がそれぞれ任意であること。
- 既存一覧のページ分割と、開発環境以外での閲覧制限。

全体では283テストが成功し、整形・Lint・型チェックも成功した。行カバレッジは92.71%、分岐は85.78%、両者を合算した総合値は91.45%だった。これらは作業時の検証結果であり、本記事の執筆時に再実行した結果ではない。

## トレードオフ・今後の懸念

日付なしや広い期間では、本文を含む大きな応答になり得る。全件取得に上限を追加しない判断は既存契約を維持したもので、応答時間やメモリー使用量の性能測定までは行っていない。分割取得が必要なら、ページ分割する`/records`を使う。

旧`/records/by-date`の呼び出し側は移行が必要になる。著者別APIでは応答項目も異なるため、URLだけの置き換えで済むとは限らない。

## まとめ

既存の全件取得へ任意の日付条件を加える場合は、「条件を省略したときに何が残るか」を契約にする。今回は著者条件と応答形式を維持し、開始日・終了日だけをそれぞれ追加した。4通りの指定と対象の分離をHTTP経由で確認したことで、利用者が選び直した取得方法を明確に実装できた。
