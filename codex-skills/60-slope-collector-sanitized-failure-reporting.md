# スクレイパーの失敗通知から本文と完全レスポンスを除外する

## 対象読者

外部HTMLを扱う収集処理で、障害調査に必要な情報を残しつつ、記事本文や取得データをログ・メールへ流出させたくない開発者向け。

## スコープ

Issue #6で追加した失敗の集約、ログレベル、通知内容を扱う。認証方式、対象サイト固有の値、メールサーバーの構築手順は扱わない。

## 問題

取得処理の失敗を調査するには、どの段階で、どの論理的な取得元について失敗したかが必要になる。しかし、例外やレスポンスをそのままログや通知へ出すと、HTML本文、記事本文、URL、設定値、認証情報が混ざる危険がある。

また、レコードごとにメールを送ると、1回の収集で大量の通知が発生する。

## 方針

失敗を次の項目だけを持つ`CollectionFailure`として集約する。

| 項目 | 目的 |
| --- | --- |
| 発生時刻 | 収集実行との対応付け |
| 段階 | 一覧、履歴、レコードのどこで起きたか |
| 論理コンテキスト | 設定上の取得元を区別する |
| 例外型 | 一時エラーか解析エラーかを調べる |
| メッセージ | 例外が提供する短い診断情報 |

記事本文、完全なHTTPレスポンス、対象固有の値、秘密情報は、ログと通知へ含めない。未解決の失敗は1回の実行が終わった時点で1通の要約通知にまとめる。

## 実装

収集結果に`failures`を追加し、各処理段階で捕捉した対象を同じ形式へ変換する。収集終了時には件数を`INFO`、再試行を`WARNING`、未解決の失敗を`ERROR`として記録する。`ERROR`ログも、失敗の段階、論理コンテキスト、例外型だけを出力する。

通知の本文には、失敗ごとに時刻・段階・コンテキスト・例外型・メッセージを出力する。1件ごとの本文やレスポンスを添付する設計にはしていない。

## 検証

受け入れテストでは、本文に相当する情報を含まない失敗を1件作り、通知本文に次が含まれることを確認した。

- `stage=record`
- `context=source_a`
- 例外メッセージ

同じテストで、レスポンス本文を通知へ渡す実装になっていないことも確認した。コード変更後の検証では、Ruffの整形・Lint、mypy、pytestが成功し、62テスト、カバレッジ86.03%を確認した。

## 制約と残存リスク

- 例外メッセージ自体が機密値を含む場合の完全な除去までは、この実装のテスト範囲に含めていない。
- 通知に含める情報は診断用の最小集合であり、失敗した入力を再現する完全な証跡ではない。
- メール送信の到達性や運用者の保管ポリシーは別途確認が必要である。

## まとめ

障害調査に必要な段階・論理コンテキスト・例外型を構造化し、本文や完全レスポンスを境界の外へ出さないことで、収集処理の可観測性とデータ保護を両立できる。失敗を実行中に集約して最後に1通へまとめると、調査に必要な情報を保ちながら通知量も制御できる。
