# 有効な日付でもUTC変換でOverflowErrorになった原因

## 結論

日本の暦日をUTCへ変換するAPIでは、日付の構文検証だけでは不十分だった。`0001-01-01`の午前0時はUTCへ変換するとPythonの`datetime`が表現できる範囲を下回るため、検索前にHTTP 400へ変換した。

## 発生した問題

### 症状

```text
OverflowError: date value out of range
```

日付範囲の開始と終了に`0001-01-01`を渡す回帰テストで、HTTP応答の確認へ到達する前に例外となった。

### 発生条件

2026年10月24日、Python 3.14.7のslope-collector。APIは日付を`Asia/Tokyo`の午前0時として扱い、`astimezone(UTC)`で検索用時刻へ変換する。

### 影響

パーサーが受け付ける日付でも、変換後に計算可能とは限らなかった。入力エラーを既存のHTTPエラー形式で返せず、処理が失敗した。

## 調査

通常の日付と年越しのテストが成功した後、表現可能な最小日付を追加した。失敗箇所はSQLの実行前で、開始時刻を作る`astimezone(UTC)`だった。DBのデータや日付の前後関係が原因ではなかった。

## 原因

日本の午前0時をUTCへ戻すと、日付が前日に移る。最小年の元日では、その前日をPythonの`datetime`として表せない。これは、開始日が終了日より後かどうかという検証とは別の境界だった。

## 解決方法

このAPIでは開始日が`date.min`の場合に、変換前に既存のエラー形式でHTTP 400を返す。

```json
{
  "code": "BAD_REQUEST",
  "message": "The start date is outside the supported UTC range."
}
```

汎用的に例外を握りつぶす変更や、保存時刻をローカル時刻へ書き換える変更は行っていない。

## 動作確認

`ba8c3be`のテストで`OverflowError`を再現し、`3dd4c4e`のガード追加後はHTTP 400となった。最大日付`9999-12-31`はUTCへ変換でき、今回の空DB範囲では200と空配列を返すテストも成功している。

終了側は翌日を加算せず、その日の`time.max`をUTCへ変換している。最大日付の次の日を作らない構成である。MySQLの保存可能期間全体を検証した結果ではない。

## 再発防止

最小・最大日付をHTTP契約の回帰テストへ残した。READMEにもUTCへ表現できない開始日を400で返すことを記載した。

## 得られた教訓

入力形式、期間の前後関係、タイムゾーン変換後の表現可能範囲は、それぞれ確認する必要があった。この検証は日本の暦日をUTCへ変換する今回のAPIを対象としており、任意のタイムゾーンへそのまま一般化しない。
