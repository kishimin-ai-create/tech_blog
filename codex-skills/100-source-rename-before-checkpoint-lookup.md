# 保存時の名前補正では遅い：チェックポイント照合前に取得元を解決する

## 結論

取得元の表示名が変わった場合の補正を保存処理に置くだけでは、保存前の重複照合に間に合わない。アーカイブ取得では、安定した内部キーによる既存行の検索と表示名の更新を、対象の解決・記事キー照合より前に実施した。

## 発生した問題

### 症状

DBに記事があるにもかかわらず、その記事の詳細リクエストが発生した。重複保存は避けられても、不要な取得が起きる。レビューでは、その詳細が取得不能なら既存記事についても失敗し得ると指摘された。この取得不能シナリオ自体を実環境で再現したとはしていない。

### 発生条件

PythonとSQLAlchemyによる取得処理で、DBの取得元行が従来の内部キー名を持ち、設定の表示名だけが変わっていることが条件だった。

### 影響

対象の仮キー解決と保存済み記事の検索が、変更後の表示名で取得元を見つけられない。保存処理に到達するまで、既存チェックポイントを使えない。

## 調査

### 照合と保存の順序を確認する

既存の保存処理には、表示名で取得元が見つからなければ安定キーで探して名称を更新する処理があった。一方、照合前の準備処理には同じフォールバックがなかった。

通常キーと仮キーを持つ対象に対して表示名を変更する回帰テストを追加した。修正前は、保存済み記事の詳細URLを要求しないというアサーションが失敗した。重複行の有無だけを検査していたら、この問題は見落とし得る。

## 原因

補正処理の存在ではなく、その実行時点が問題だった。新しい表示名でチェックポイントを検索した時点では、DBの取得元名はまだ古いままだった。

## 解決方法

対象の準備処理へ安定キーも渡し、表示名検索が不一致の場合だけ、従来の内部キー名の行を探して名称を更新した。その後に対象の解決と記事キー検索を行う。

次は処理順序を示す説明用の抜粋であり、クエリの完全な実装ではない。

```python
source = find_by_display_name(configured_name)
if source is None and configured_name != stable_key:
    source = find_by_display_name(stable_key)
    if source is not None:
        rename_source(source, configured_name)
resolve_entity(source)
check_existing_article_keys(source)
```

準備処理はトランザクション内で実行する。対象の移行候補が曖昧で例外になった場合、途中の名称更新も確定させない。

## 動作確認

表示名変更の有無と、通常キー・仮キーの組み合わせでテストした。既存詳細へのアクセスがないこと、元の対象IDと状態が保たれること、取得元名が設定名へ更新されることを確認した。

**FACT:** 修正を含む全体検証で115テストが成功し、Ruffの整形・Lintとstrict mypyも成功した。総合カバレッジは88.81%だった。

## 再発防止

保存結果だけでなく、保存までに発生した詳細リクエストも回帰テストの観測対象にした。記事が既存なら保存件数は0、という検査だけでは外部アクセスの増加を検出できない。

## 制約

これは従来の内部キー名から設定名へ移すためのフォールバックであり、任意の過去の表示名を追跡する仕組みではない。変更履歴全般を扱うなら、別の永続的な取得元識別子が必要になる。
