# レビュー練習用の変更を、小さな積み上げPRとして渡す

## 結論

AIに実装を任せ、人間がレビュワーになる練習では、作業を止める頻度とPRの大きさを別々に決める必要がありました。profile-hubでは作業を継続しながら、後続PRのbaseを直前の作業ブランチにして、目的ごとの差分を渡しました。

確認日は2026年10月27日です。対象は公開サイト基盤のIssue #16で、PR #40〜#52を作成しました。公開時点では13本ともOpen・未マージです。レビュー練習の効果や、レビュー所要時間はまだ確認していません。

## 背景と制約

ユーザーは意図的な欠陥を混ぜる形式ではなく、通常どおり実装したコードをレビューする形式を選びました。また、実装のたびに確認して止まることは求めておらず、1つのPRを小さく保つことを求めていました。

最初はルーティングと共通レイアウトをまとめる案でしたが、最初のPRを5ルートと404の接続だけへ縮小しました。ホームの入口リンク、ナビゲーション、スタイルは後続へ分けています。

## 検討した分け方

| 方法                       | 変更の継続     | レビューに出す差分                           |
| -------------------------- | -------------- | -------------------------------------------- |
| 毎回確認して停止する       | 指示待ちになる | 小さくできるが、停止自体は今回の要望ではない |
| 後続もmain向けにする       | 継続できる     | 未マージの前提変更も差分へ含まれる           |
| 直前のブランチをbaseにする | 継続できる     | 前提との差分をPRごとに示せる                 |

採用したのは3番目でした。たとえばホームの入口だけを追加するPR #41は、ルーティングを追加したPR #40のブランチをbaseにしています。

```text
main
└─ feature/16-public-routes             PR #40
   └─ feature/16-home-section-links     PR #41
      └─ feature/16-section-navigation  PR #42
```

## 実装後に確認したこと

[PR #40](https://github.com/kishimin-ai-create/profile-hub/pull/40)は6ファイル・追加107行・削除15行、[PR #41](https://github.com/kishimin-ai-create/profile-hub/pull/41)は2ファイル・追加29行・削除2行でした。後続の状態別Storybookは、[PR #49](https://github.com/kishimin-ai-create/profile-hub/pull/49)として1ファイル・追加27行に分かれました。

これらはGitHubから読み戻した差分量です。「小さい」という評価だけで済ませず、目的とファイル数・行数を合わせて確認しました。

## CIとマージは別の確認になる

このリポジトリのPRワークフローは、baseがmainの場合だけ起動する設定でした。PR #40のCI成功は確認しましたが、後続の積み上げPRには同じPR用CIが自動で走りません。ローカルで検証した事実とCI成功を区別して記録しています。

この方式はbaseの管理も必要です。先行PRのマージ後には、後続のbaseと差分を再確認する必要があります。その運用を完了した事例ではありません。

## 学びと適用範囲

今回作れたのは、レビューする順番と対象差分が明確な教材です。ユーザーのレビュー結果、修正の往復、全PRのマージは今後の作業です。PR数を増やすこと自体を目的にせず、レビュワーに判断してほしい変更の目的で分割しました。
