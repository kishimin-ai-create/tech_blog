# Docker更新後の収集コマンドを実行環境と設定から検証する

## 結論

追加取得元のDocker更新では、ビルド成功に加えて、コンテナのPython、実行用設定、DB接続、実際の収集コマンドを確認した。システムPythonでは依存ライブラリを読めず、仮想環境のPythonへ切り替えた後もUser-Agent未設定で停止した。両方を修正して実コマンドの成功を確認した。

個人名、連絡先、実取得元、DB認証情報、対象ID、端末内パスは掲載しない。

## 発生した問題

### 症状

コンテナ内の最初のPython実行で `ModuleNotFoundError` が発生した。仮想環境へ切り替えた後の取得では、User-Agent必須の検証エラーが発生した。

### 発生条件・影響

ホストはWindows、APIとDBはDocker Composeで動作する。APIは起動できても、別の実行経路である収集コマンドが成功するとは限らなかった。

## 調査

ホストの非公開設定と、Composeの `env_file` が渡す設定を確認した。ホスト側へ追加した取得元設定は、コンテナの実行用ファイルにも反映する必要があった。

コンテナでは依存ライブラリが `/app/.venv` に配置されていた。システムの `python` を使う呼び出しを `/app/.venv/bin/python` へ切り替えると設定読み込みとDB接続は成功した。その後の実取得で、実行用設定のUser-Agent不足を確認した。

## 原因

**FACT:** 依存ライブラリがあるPythonと実行したPythonが異なっていた。さらに、コンテナへ渡した設定に収集コマンドが要求するUser-Agentがなかった。設定読み込み、APIの起動、収集時の検証は別の確認だった。

## 解決方法

非公開の実行用設定へ追加取得元とUser-Agentを反映し、APIを再作成した。DBコンテナとデータは維持した。

次は作業で使用したサービス操作である。プロジェクトルートで実行し、APIの再作成による一時停止を伴う。取得元の機密設定は表示しない。

```powershell
docker compose --env-file .env.development up -d --build --no-deps api
```

収集コマンドには `/app/.venv/bin/python -m app.collector` を使う。取得対象と設定ファイルの実引数は非公開とする。

## 動作確認

| 確認 | 観測結果 |
| --- | --- |
| API・DBコンテナ | healthy |
| ホストからAPIのヘルスチェック | 正常応答 |
| コンテナの取得元設定読み込み | 成功 |
| コンテナからDBの `SELECT 1` | 成功 |
| 実アーカイブコマンド | 失敗なし、保存済み記事をスキップ |

**FACT:** 実コマンドは一覧へアクセスし、既存チェックポイントを使って詳細取得を省略した。コンテナ内での新規記事保存や全対象の完全性までを、この再実行だけで保証するものではない。

検証用にコピーした設定ファイルは終了後に削除した。コピー時の所有者がアプリ実行ユーザーと異なり、そのユーザーでは削除できなかったため、ファイルを限定して管理者権限で片付けた。

## 再発防止

**PROPOSAL:** 更新の確認項目を、イメージ、実行Python、コンテナ設定、DB、実コマンドに分ける。ホスト側の成功結果をそのままコンテナの成功として扱わず、実行環境を記録する。
