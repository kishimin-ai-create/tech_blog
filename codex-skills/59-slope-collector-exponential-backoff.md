# スクレイパーの一時的な失敗を指数バックオフで再試行する

## 対象読者

外部HTTPサービスからページを取得するバッチやスクレイパーを、途中の一時的な通信失敗で全体停止させたくない開発者向け。

## スコープ

Issue #6で実装した取得処理の再試行とバックオフを扱う。定期実行のスケジューリング、実サイトの取得結果、対象サイト固有の設定は扱わない。

## 背景

一覧ページや詳細ページを順番に取得する処理では、ネットワークエラー、HTTP 5xx、HTTP 429のように、同じ要求を後から再実行すれば成功する可能性のある失敗がある。この種の失敗を1回の例外として扱うと、取得済みデータまで含めた処理全体の再実行が必要になる。

一方で、HTMLの契約違反や恒久的なHTTPエラーまで無制限に再試行すると、相手への要求を増やし、原因の発見も遅れる。

## 方針

今回の実装では、再試行対象を`FetchTemporaryError`に限定し、最大3回まで試行する。待ち時間は環境変数`COLLECTOR_RETRY_BACKOFF_SECONDS`で設定し、既定値を1秒とした。

```text
1回目の失敗 -> 1秒
2回目の失敗 -> 2秒
3回目の失敗 -> 失敗として確定
```

実際の待機は注入した`睡眠関数`で行えるため、受け入れテストでは外部の時計を止めたまま待ち時間を検証できる。

## 実装

再試行の責務を`_retry`へまとめ、処理本体は「一覧を解析する」「詳細を解析する」という操作だけを渡す形にした。

```python
for attempt in range(MAX_ATTEMPTS):
    try:
        return operation()
    except FetchTemporaryError:
        if attempt == MAX_ATTEMPTS - 1:
            raise
        delay = backoff_seconds * (2**attempt)
        sleep(delay)
```

解析契約のエラーは再試行しない。最後まで解消しなかった取得エラーは収集結果へ記録し、後続レコードの処理を続ける。これにより、成功したレコードは即時保存され、失敗だけを実行結果から確認できる。

## 検証

受け入れテストでは、一時エラーを2回発生させて3回目に成功する操作を使い、次を確認した。

- 操作が3回呼び出される
- 待ち時間が`[2.0, 4.0]`になる設定で、指数的に増える
- 成功値が呼び出し元へ返る

リポジトリ全体では、Ruffの整形・Lint、mypy、pytestを実行し、62テストが成功した。カバレッジは86.03%で、設定された80%以上を満たした。

## 制約と残存リスク

- 3回の試行で解消しない失敗は自動回復しない。
- バックオフは要求間隔とは別の設定であり、相手サービスの利用規約や負荷上限を置き換えない。
- 実サイトを呼び出す本番収集の成功件数や所要時間は、このテスト結果からは判断できない。

## まとめ

一時的な通信失敗だけを対象に、試行回数を3回へ制限し、設定可能な指数バックオフを入れると、無制限な再試行を避けながら短時間の障害へ対応できる。待ち時間を関数として注入すると、実際に待たずに再試行回数と遅延をテストできる。
