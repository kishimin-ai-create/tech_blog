# APIが受け付けた作品URLを公開画面でも扱う

## 結論

管理画面とAPIが受け付けた作品URLを、公開画面だけが拒否する不整合を修正した。公開側もURLパーサーで正規化し、プロトコルはHTTPとHTTPSに限定する。[PR #261](https://github.com/kishimin-ai-create/profile-hub/pull/261)はドラフトで、アプリのmainには未マージである。

## 問題と原因

作品URLのAPIスキーマと管理画面は`new URL()`で解釈できるHTTP・HTTPS URLを受け付けていた。一方、公開側には`http://`または`https://`で始まることを別途要求する検査があった。

例えば`https:example.com`はAPIスキーマで受け付けられ、URLパーサーでは`https://example.com/`になる。しかし以前の公開側の接頭辞検査はこの値を拒否し、対象作品を含む一覧がエラーになった。

## 対応と検証

公開側でも文字列をURLとして解析し、解析後のプロトコルがHTTPまたはHTTPSの場合だけ正規化したURLを使用する。無効な文字列や`javascript:`は拒否する。

- APIスキーマが`https:example.com`を受け付けることを確認した。
- 公開画面のテストで、その形式が正規化されてリンクとして表示されることを確認した。
- リポジトリ・デモ・画像の各URL欄に危険なスキームを渡し、拒否されることを確認した。
- 公開画面の全テストと型チェック、Lint、markup lint、整形チェックは成功した。

独立したセキュリティ専門家によるレビューは未実施である。今回の検証は外部URLの安全性全般を保証するものではない。

## 学び

同じデータを保存する側と表示する側が別の形式検査を持つと、保存済みの値で表示が失敗する。契約を照合するときは正常な入力だけでなく、パーサーが正規化する形式と危険なスキームの両方を検証する。
