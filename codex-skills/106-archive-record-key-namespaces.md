# 対象の同一性を保ちながら過去の記事ID衝突を防ぐ

## はじめに

過去と現在で取得サイトが変わった対象の履歴を、既存のDB対象行へ保存した。この記事は、対象IDの引き継ぎと、独立した記事ID体系の衝突回避を分けて扱った記録である。実際の人物・団体・サイト・識別子は掲載しない。

## 背景

対象を別の行に作り直すと履歴が分断される。一方、記事の数字だけを現在の取得元へ持ち込むと、独立した旧サイトの記事IDと現在の記事IDを区別できない可能性がある。対象の同一性と記事キーの一意性は別の問題だった。

## 目的

既存の対象IDと状態を維持しつつ、旧体系の記事キーを区別して手動バックフィルする。

## 当初の想定

既存対象へ過去の履歴を保存することが要求されていた。重複するIDの実測頻度や性能目標は設定していない。

## 実際にやったこと

元のHTMLから取得した著者と記事IDを検証した後、保存用の対象キーを既存のものへ割り当てた。`record_key_namespace` が設定されている場合は記事キーに接頭辞を付ける。

次は実キーを使わない説明例である。同一のID体系を共有する通常取得とアーカイブに、無条件で接頭辞を付ける設計ではない。

| 概念 | 説明例 |
| --- | --- |
| 保存先の対象ID | 過去・現在とも既存の同じ対象行 |
| 現在の記事キー | `42` |
| 独立した旧体系の記事キー | `legacy:42` |

## 実際の結果

**FACT:** `app/services/archive_collection.py` の `_parse_original_html` は著者・記事IDの確認後に保存用対象キーを割り当てる。記事キー生成は設定された名前空間を反映する。ローカル取得とDB照合で既存対象の引き継ぎを確認した。

## 良かったこと

取得経路、保存先の対象、記事キーの体系を分けて扱えた。対象行を増やすことで記事IDの問題を解決しようとする必要がなくなった。

## うまくいかなかったこと

一覧に載る記事でも、詳細が元サイトとアーカイブの双方で404となるものは保存できなかった。キーの設計だけでは到達不能な本文を回復できない。

## 想定との差

対象行の引き継ぎは確認できた。一方、過去の記事をすべて取得できるかは詳細ページの到達状態に依存した。事前の件数予測がないため、予測との差は算出していない。

## 学んだこと

**INFERENCE:** 同一対象へ保存する場合でも、記事IDが同じ発行体系かを別に確認すると、履歴の分断とキー衝突をそれぞれ扱える。名前空間を後から変更するとチェックポイントも変わるため、再実行前に固定する必要がある。

## 次回どうするか

対象の対応付け、記事ID体系、元ページの著者確認、保存後の集合照合を別々の確認項目にする。この記事は同一人物を名前だけで一般的に判定できると主張するものではない。
