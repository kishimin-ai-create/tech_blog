# プロンプト棚卸しの9候補を新規2件と既存6件のSkillへ整理した

## はじめに

定期分析が挙げた「5件以上」の作業候補をもとに、2026年10月21日に共有Skillを整備した。件数をそのまま新規Skill数に変換せず、既存の責務と重複するものは補強した。

## 前提・環境

分析の件数は7日間の異なるプロンプトログ行数であり、独立した作業回数ではない。同じ作業の訂正や追加指示も含む。この制約を確認したうえで、5件以上の9項目を対象にした。

## やってみた結果

9項目を、新規2件・既存6件のSkillへ整理した。レビュー指摘の翻訳は既存のレビュー対応Skill内の参照テンプレートにし、別の実行コマンドは追加しなかった。

| 候補 | 対応 |
| --- | --- |
| 記事推敲・19行 | `article-patterns`へ参加記事の参照資料を追加 |
| 選択コミット・8行 | `commit-changes`で対象・除外と残存差分を明確化 |
| レビュー返信・7行 | `github-address-pr-comments`の依頼範囲を明確化 |
| レビュー翻訳・5行 | 同Skillに翻訳だけの経路とテンプレートを追加 |
| 未取得分収集・5行 | `collect-missing-records`を新設 |
| 停止通知・5行 | `verify-stop-notification`を新設 |
| APIの型とSchema・5行 | `typescript-type-safety`へ契約調査の参照資料を追加 |
| HTML表示調整・5行 | `frontend-display`へ静的HTMLの調整手順を追加 |
| 構成と競合・5行 | `frontend-folder-structure`へ競合の診断手順を追加 |

## 実装・検証

### 判断を変える箇所だけを補う

記事推敲では、登壇者の発言と筆者の体験・感想を混同しないことを補った。翻訳だけの依頼ではコード修正やGitHub投稿へ進まない経路を置いた。新規の収集・通知Skillも、手順を記述すること自体が実行や送信の許可にならないようにした。

詳しい条件分岐は必要時だけ読む参照資料へ置き、既存Skillの本文へ全手順を重複掲載しなかった。実行スクリプトは追加していない。

### 構造検証と内容確認を分ける

```powershell
python -X utf8 "$HOME/.codex/skills/.system/skill-creator/scripts/quick_validate.py" "$HOME/.agents/skills/article-patterns"
```

対象8件すべてへ同じ検証を実行し、最終的に`Skill is valid!`を確認した。13ファイルのUTF-8、余分な空白、相対リンクとGit差分も確認した。変更はSkillごとの8コミットへ分けた。

## つまずいたところ

構成関連Skillの既存descriptionには`features/<feature>/...`という列挙があり、検証器が`Description cannot contain angle brackets (< or >)`を返した。本文のフォルダ例は維持し、descriptionを用途が分かる短い文章へ変更すると検証を通った。

これはdescriptionの制約に対する修正であり、本文内のすべての山括弧を削除する規則ではない。検証器の対象フィールドを確認して対処した。

## 学んだこと

プロンプトの多さは確認候補を選ぶ材料になるが、手順が安定している証拠とは限らない。既存Skillへ追加するか、参照テンプレートにするか、新設するかを責務から選んだ。

構造検証は名称やfrontmatterなどを確認するもので、実際のモデル挙動の保証ではない。今回は差分と依頼範囲を内容レビューしたが、独立したエージェントによる実行評価や、運用改善の効果測定は実施していない。
