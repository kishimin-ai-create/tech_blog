# カバレッジに80%と表示されても、分岐が80%以上とは限らなかった

## 結論

カバレッジの閾値は、表示用に丸めた数字ではなく、元の分子・分母やJSON内の数値で判定する。glyph-forgeの検証途中では、分岐カバレッジが107/134、約79.85%だったが、表示用の値は`80`だった。

対象はpytest-covのレポートを品質判定に使う人である。2026年10月22日、Python 3.12.4、pytest 7.4.4、pytest-cov 7.0.0、coverage 7.13.1で得たレポートを扱う。

## 発生した問題

### 症状

全体の総合カバレッジが約88.76%に達していても、分岐だけを取り出すと80%に届いていなかった。

```text
covered_branches: 107
num_branches: 134
percent_branches_covered: 79.85074626865672
percent_branches_covered_display: '80'
```

これは中間の実行結果である。最終レポートの数値ではない。

### 発生条件と影響

今回の完了条件は、全体サマリーに報告される各指標が80%以上であることだった。総合値だけで判断したり、表示用の`80`をそのまま数値比較したりすると、この条件を満たしていない状態を完了扱いにしてしまう。

## 調査

### 測定対象と指標を分ける

`app`と`src/glyph_forge`の両方を測定対象にし、分岐も収集した。

```powershell
python -m pytest -o addopts= -q --cov=src/glyph_forge --cov=app --cov-branch --cov-report=term-missing --cov-report=json:output/issue-5-coverage.json
```

このコマンドはglyph-forgeのリポジトリルートで実行した。JSONの`totals`には、文・行、分岐、総合の値と、表示用の値が分かれて入っていた。このフィールド構成は今回使ったcoverage 7.13.1での確認である。

### 丸める前の値を確認する

107/134を100倍すると約79.85になる。表示の`80`と、条件式`>= 80`が同じ意味ではないことを、レポートの数値から確認できた。分岐を計測していないレポートに、この判定をそのまま適用してはならない。

## 原因

総合値と分岐値は別の指標であり、表示用の値には丸めがある。今回の閾値は分岐にも適用されるため、総合値の達成だけでは判定できなかった。

## 解決方法

対象の描画機能に不足していた、既定設定での枠描画・アップロード画像への絵文字の埋め込み・キャンバスへ収まる場合の検証を追加した。閾値のために無関係な機能を変更したり、失敗を捏造したりはしなかった。追加した互換性・境界ケースが最初から成功した事実も、Redの回帰テストとは区別した。

最終結果では分岐が108/134になり、丸め前の値で80%以上を確認した。レポートを読む一回限りの確認では、次の条件を使った。

```python
import json

with open("output/issue-5-coverage.json", encoding="utf-8") as report:
    totals = json.load(report)["totals"]

assert min(
    totals["percent_statements_covered"],
    totals["percent_branches_covered"],
    totals["percent_covered"],
) >= 80
```

これは当該JSONに対するローカル確認である。この判定をリポジトリのCIへ常設した変更は行っていない。

## 動作確認

| 最終レポートの全体指標 | 値 |
| --- | ---: |
| 文・行 | 597/658、90.72948…% |
| 分岐 | 108/134、80.59701…% |
| 総合 | 89.01515…% |

全体テストは151件成功、Windowsの環境条件で5件スキップだった。スキップした5件は、別途Linuxコンテナで実行して成功した。ただし、上のカバレッジ値はWindowsの実行結果であり、Linux側の結果をマージした値ではない。

## 再発防止

次回も測定対象、必要な指標、丸め前の値を揃えて判定する。表示用の数字は読みやすさのために使い、機械的な閾値判定には使わない。カバレッジを増やしたこと自体がテストの妥当性を保証するわけでもないため、追加ケースには利用者が観測できる振る舞いを対応させる。

## まとめ

今回の落とし穴は、テストの成否ではなくレポートの読み方にあった。総合値が高くても分岐は未達になり得る。表示値と計算値を区別すると、境界の79.85%を80%以上と取り違えずに済む。
