# 復旧確認を1分間隔にすると実行が重なった原因と修正

## 結論

次回予定を確認間隔だけで設定していたため、確認処理が終わる前に別の実行が同じ対象を取得できた。確認間隔と、確認に必要な応答期限・待機時間の両方を考慮して、実行の予約期限を決める修正を入れた。

これはslope-collectorの開発中に回帰テストで再現した問題であり、本番で起きた障害ではない。

## 発生した問題

自動復旧確認は、一覧と記事1件を取得する。設定可能な間隔の最小値は1分だが、HTTPの応答期限はそれより長く設定できる。

### 症状

確認中に次の実行を模擬すると、2つ目も対象を取得していた。

```text
assert second_claims == [0]
E assert [1] == [0]
```

### 発生条件と影響

2026年10月24日、Windows・Python 3.14.7で検証した。テストでは確認間隔を1分、応答期限を90秒に設定した。最初の確認は開始から1分後に実行し、そのHTTP応答の途中で、開始から2分後の別実行を呼び出した。

この条件では、最初の確認が進行中でも予約期限を過ぎ、外部サイトへの確認が重なり得る。

## 調査

DB上で対象を取得するとき、revisionの一致と期限到来を条件に更新していた。同時に同じ期限を取得する競合は防げるが、更新後の次回予定が「現在時刻＋確認間隔」だけだった。

`test_recovery_worker_cannot_claim_an_inflight_short_interval_check`で、最初のHTTP処理中に別の復旧確認を呼び出した。2つ目の`checked`が1になる失敗を確認した。

## 原因

通常の確認間隔と、実行中の処理を他の実行から保護する期間を、同じ長さとして扱っていたことが原因だった。古い結果の適用をrevisionで防いでも、先に送った外部通信までは取り消せない。

## 解決方法

確認処理を取得した際の予約を、確認間隔と確認予算の長い方にした。今回の確認予算は次の式で計算する。

```text
2 × (応答期限 + 要求間隔 + ジッター上限) + 60秒
```

2回の応答と待機に、解析用の余裕を加えている。通常の確認失敗が完了したら、次回予定は完了時刻から利用者指定の間隔で設定し直す。予約期間を毎回の通常間隔に置き換えたわけではない。

処理が途中で終了した場合は停止状態を保持し、予約期限後の実行が再確認できる。タイマーも専用のoneshotサービスとして動かすが、DBの予約は別プロセスからの実行にも適用する。

## 動作確認

修正後は同じ再現テストで`second_claims == [0]`となった。テストの実行場所はslope-collectorのルートである。

```powershell
uv run pytest tests/medium/test_collection_control.py tests/medium/test_recovery_checks.py -q --tb=short
```

修正時点のこのコマンドは19件成功した。その後に境界ケースを追加した最終の全体検証は256件成功、総合カバレッジ91.21%だった。実MySQLと実サイトでの重複実行検証は行っていない。

## 再発防止と制約

1分の間隔と90秒の応答期限を組み合わせる回帰テストを残した。予約には解析の余裕を含めているが、任意に長いプロセス停止や解析時間を保証する仕組みではない。予約期限と応答期限、通常の確認間隔を分けて読み取れることが、今回の再利用可能な知見である。
