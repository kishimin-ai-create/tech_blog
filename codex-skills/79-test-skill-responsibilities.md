# テスト設計Skillは判断と実行の責務を分ける

## 要約

テストに関する大きな要求をAI Skillへ移すときは、テストの品質をどう判断するかと、統合テストをどの境界でどう動かすかを分けると、既存のケース設計・実装パターン・TDD・ATDDと役割を重ねずに済む。今回、テスト設計の考え方をまとめた要件を2つのSkillへ整理し、既存Skillとの境界を本文に記した。

この記事は、Codexなどで再利用するSkillを設計・保守する開発者向けである。テスト技法の完全な解説や、書籍の内容を原文から検証したレビューではない。

## 要求をそのまま1つのSkillへ詰めない

今回の入力には、単体テストの学派、4本柱、テスト技法、テストダブル、統合テスト、privateメンバー、日時などの非決定的な依存、TDD・ATDDとの関係が含まれていた。

この内容を単一の長いSkillへまとめると、利用者が「モックの使い方を選びたい」のか「統合テストを並列にするか判断したい」のかで、同じ説明を毎回読み込むことになる。一方、細かく分割し過ぎると、どのSkillを使うかを選ぶ負担が増える。そこで、横断的なテスト設計の判断と、統合テスト固有の実行戦略を分けた。

## 2つのSkillに分けた責務

| Skill | 答える問い | 主な判断 |
| --- | --- | --- |
| `test-design-quality` | このテストは何を保証し、どの方法で確かめるか | 観察可能な振る舞い、古典学派とロンドン学派、出力値・状態・コミュニケーションの選択、モック境界、4本柱 |
| `integration-test-strategy` | どの結合を統合テストで検証し、どう実行するか | 実際に通す外部境界、単体テストとの分担、直列を初期方針とする理由、並列化の条件、テストケース間の独立性 |

統合テストの直列実行は、今回の要件に含まれた初期方針として記述した。共有DBや外部サービスを分離するコストが並列化の利益を上回る場合がある一方、環境とデータの分離ができて利益が明確なら並列化できる。直列にしただけでテスト間の依存が許されるわけではないため、ケース単独でも結果が変わらない条件を別に残した。

## 既存Skillと役割を接続する

新しいSkillが既存の仕組みを置き換えないよう、処理の段階ごとに責務を明記した。

| 作業 | 主に使うSkill |
| --- | --- |
| 要件からテストケースを分解する | `test-case-design` |
| テストの品質と依存境界を判断する | `test-design-quality` |
| 統合テストの実際の境界と実行方式を決める | `integration-test-strategy` |
| 言語・ランナーに沿った書き方を選ぶ | `test-patterns` |
| Red → Green → Refactorで実装する | `tdd` |
| 受け入れテストを先に確定し保護する | `atdd` |

たとえば、ケース設計はブラックボックスの仕様から始め、実装を分析するときはホワイトボックスで重要な分岐や失敗経路の漏れを探す。見つけた漏れは、できるだけ公開された振る舞いとしてテストする。テスト設計Skillはこの判断を担い、個別のVitestやxUnitのコード例は`test-patterns`など既存の実装Skillに任せる。

## 書籍由来の原則と適用先の決定を分ける

今回の要件文書は『単体テストの考え方／使い方』に基づく考え方を整理したものだった。作成したSkillでは、古典学派とロンドン学派の違い、4本柱、出力値・状態・コミュニケーションベースの使い分けを、その要件文書の範囲でまとめた。書籍本文を参照して照合したわけではないため、記事やSkillを原文の引用・検証として扱わない。

また、テストサイズやファイル名、CIのルールは適用先リポジトリの決定に従う。たとえばこの共有環境では、ADR-0004がテストサイズ名、ADR-0032が純粋な変換とHTTP輸送境界の分離、ADR-0044がテスト種別とサイズ軸の分離を定めている。これらのローカル規則を、書籍由来の一般原則として混ぜない。

## 検証結果と限界

2つのSkillに対してSkill Creatorの`quick_validate.py`を実行し、どちらも`Skill is valid!`となった。`git diff --check`も成功し、要件書の第1〜11節がどちらかのSkillに対応することを確認した。変更はコミット`331d093`で記録した。

この検証はSkillのfrontmatter、名前、未完了のひな形などを確認するもので、実際の依頼でSkillが期待どおり選択されることや、テスト設計の判断が改善したことまでは証明しない。独立した実行シナリオによる評価は行っていない。また、書籍そのものとの逐語的な照合もしていない。

## まとめ

大きなテスト要件をSkillにする際は、「テストをどう評価するか」と「特定の層をどう実行するか」を分け、ケース設計・コードパターン・TDD・ATDDの既存責務へ接続できる。形式検証は必要だが、Skillの実際の選択や判断品質の検証とは別である。
