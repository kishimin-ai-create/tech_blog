# メンテナンスからの復旧はHTTP 200だけで判定せず、一覧と記事を解析する

## 結論

slope-collectorの自動再開は、一覧ページと最初の記事1件を既存の契約どおりに解析できた場合だけ許可した。HTTP 200でメンテナンス画面が返るケースを、復旧と取り違えないためである。

2026年10月24日、Windows・Python 3.14.7でHTTP応答をモックして検証した。実サイトの復旧を観測した記録ではない。

## 背景と課題

メンテナンス終了時刻が不明な場合、停止したまま忘れずに再開したい。一方、確認のたびに全記事を収集すると、停止中の通常処理を抑える目的から離れる。

今回は停止時に手動再開と自動再開を選び、自動の場合だけ専用コマンドで低頻度の復旧確認を行う。確認間隔は既定60分、1〜1,440分の整数とした。

## 前提・制約

- 確認処理は記事を保存しない。
- 手動再開は外部確認をせず、利用者の操作で解除する。
- 自動解除しても、その場で収集は始めない。
- 取得元のURLやセレクタは既存の非公開設定を使う。

## 検討した選択肢

### Option A：一覧だけ解析する

確認に必要な要求は少ない。ただし一覧が戻り、記事本文はまだ取得できない状態を見分けられない。

### Option B：一覧と記事1件を解析する

確認の要求数が増えるが、記事取得まで含めて利用可能かを確かめられる。今回はこの条件を選んだ。

| 評価軸 | 一覧のみ | 一覧と記事1件 |
| --- | --- | --- |
| 一覧の解析契約 | 確認する | 確認する |
| 記事本文の解析契約 | 確認しない | 確認する |
| 対象リソース数 | 1 | 2 |

HTTPステータスの成功だけでは、どちらの解析契約も確認できない。実装では既存の`SourceAdapter`とアーカイブ用解析処理を再利用した。

## 実装と確認範囲

公式側は一覧の最初の参照から記事を1件取得し、本文などを解析する。アーカイブ側も同じ方針で、JSON形式とHTML形式の両方を扱う。メンバーを指定した確認では、そのメンバーとの対応も確認する。

確認先はローカルの非公開JSONに定義する。管理APIから任意のURLを受け取る形式にはしなかった。対象が設定されていない自動停止の要求には409を返し、状態を変更しない。

```json
[{"source": "source_a", "site": "official"}]
```

これは公式確認の最小設定例である。実際の接続先は通常の収集設定から読み、アーカイブでは対象メンバーと既存のアーカイブ契約ファイルも指定する。

## 実装後の結果

テストでは一覧・記事それぞれのHTTP 200メンテナンス画面、503、アーカイブの不正な著者や不足フィールドを返した。失敗時は停止を維持し、次の確認を完了時刻から設定した。成功時は停止を解除し、記事の保存件数は0のままだった。

確認コマンドは`uv run python -m app.collector check-recovery`であり、即時の再試行や再開通知は行わない。次回の日次収集または手動実行が通常の収集を担う。

## トレードオフ・今後の懸念

記事1件が解析できても、すべての記事や画像配信元の復旧までは保証できない。確認用メンバー自体に記事がなくなれば判定できなくなるため、代表となる対象の設定は運用で維持する必要がある。実サイト、実MySQL、Linuxのタイマー実行は未検証である。
