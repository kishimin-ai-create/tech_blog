# DiscordのWebhook投稿を定期タスクの設定から読み戻す

## はじめに

Discordの投稿リンクを受け取り、その内容を調べようとした。ブラウザ経由では取得できなかったが、投稿元の定期タスクから既存のWebhook設定を見つけ、同じWebhookが送った既知IDの投稿を取得できた。

## 前提・環境

- Windowsのタスクスケジューラーで分析処理を定期実行。
- 分析結果はローカルSQLiteへ保存し、要約をDiscordへ送信。
- 調査対象のメッセージIDは投稿リンクから分かっていた。
- Webhook URLは既存のローカル設定に保存済み。

## やってみた結果

Webhookメッセージ取得APIがHTTP 200を返し、対象投稿の本文を取得できた。ユーザーにWebhook URLやトークンをチャットへ貼ってもらう必要はなかった。新たなDiscord投稿や定期タスクの変更は行っていない。

## 実装・検証

### 投稿リンクとWebhook URLを分ける

チャンネルの投稿リンクにはメッセージIDがあるが、Webhook認証情報は含まれない。公式仕様には、Webhook IDとトークン、メッセージIDを指定して、そのWebhookが投稿したメッセージを取得するAPIがある。

```http
GET /webhooks/{webhook_id}/{webhook_token}/messages/{message_id}
```

これはエンドポイントの構造であり、実際の秘密値は掲載しない。任意のチャンネル履歴を列挙するAPIとして扱わない。

### 定期タスクから設定の参照先を追う

`Get-ScheduledTask`で該当処理を探し、アクションの実行ファイル、引数、作業ディレクトリを確認した。引数に設定ファイルとSQLite保存先が指定されていた。

送信処理のコードには`load_webhook`とURL検証処理があった。保存済み設定をそのコードで読み、トークンを出力せずDiscordの取得APIへ使用した。今回の実装は`discord.com`へ接続し、リダイレクト先へ秘密値を渡さない形だった。

## つまずいたところ

最初は本文の貼り付けや設定場所の提示をユーザーへ求めたが、定期実行の情報を先に調べれば所在を確認できた。

また、最初の取得自体はHTTP 200だったものの、標準出力の文字エンコーディングで日本語本文の表示に失敗した。UTF-8出力へ変更すると読めた。取得失敗と表示失敗は別だった。

## 学んだこと

外部サービスへアクセスできないときでも、既存の自動処理が使っている正規の経路が残っている場合がある。設定の所在はジョブの引数から追い、秘密値を新たな文章や公開資料へ転記しない。

投稿の読み戻し成功は、通知の端末側ポップアップまで確認した結果ではない。今回確認できたのは、指定した投稿の本文がDiscordから取得できたことである。
