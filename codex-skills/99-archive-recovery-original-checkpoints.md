# 取得元が変わっても元の識別キーで重複を防ぐ

## はじめに

通常の取得元で履歴を開けなくなった対象を、別のアーカイブから補完した。取得経路を変えるときに重要なのは、保存先で対象と記事の識別キーを変えないことである。

この記事はチェックポイントの引き継ぎを扱う。対象者名、実サイト、実際の識別キー、記事内容、対象別件数は掲載しない。

## 前提・環境

Python、SQLAlchemy、ローカルDBを使う取得処理で検証した。元の取得元に属する対象キーと記事キーを保存済みデータの照合に使い、アーカイブ固有のキーはリクエストの組み立てにだけ使う。

## やってみた結果

**FACT:** アーカイブの一覧を取得した後、保存済みの記事キーを調べ、既存記事の詳細取得を省けた。再実行では新規保存と記事詳細へのリクエストがともに0だった。取得元の一覧とDBの記事キー集合も一致した。

新規の対象は非アクティブとして保存し、既存対象のアクティブ状態は維持した。非アクティブになったことだけを理由に、保存済み履歴を別対象へ作り直す処理にはしていない。

## 実装・検証

### 取得用のキーと保存用のキーを分ける

アーカイブの対象キーで一覧を要求する一方、DB照合には元の対象キーを渡す。次は実装の順序を示す説明用の抜粋であり、単体で実行するコードではない。

```python
references = fetch_archive_page(archive_entity_key)
known = existing_record_keys(source_name, original_entity_key, article_keys)
for reference in references:
    if reference.article_key in known:
        continue
    persist_with_original_identity(fetch_detail(reference))
```

重複判定を保存時だけに置くと、重複行を作らなくても不要な詳細リクエストは発生する。一覧と詳細の間にチェックポイント照合を置くことで、この要求も省く。

### 古い対象行を照合前に引き継ぐ

古いデータには、元の対象キーを持たない仮キーの行があった。同じ取得元の候補を探し、Unicode正規化と空白除去後の名前が一意に一致する場合だけ、既存行へ元のキーを設定した。

この処理は名前だけで一般的に個人を識別できると主張するものではない。限られた移行候補の中で一致が一意であることを条件にし、複数候補が一致した場合は失敗として処理を止める。既存のDB ID、記事、状態は引き継ぐ。

### 保存済み詳細へアクセスしないテスト

通常キーと仮キーの両方について、既存記事と新規記事が同じ一覧に現れるテストを用意した。既存記事の詳細URLが要求されないこと、対象のDB IDと非アクティブ状態が保たれることを確認した。

## つまずいたところ

表示名が変わった取得元を照合前に引き継げず、保存済み記事の詳細へ再アクセスする不具合が見つかった。これは対象キーの設計とは別に、照合の起点となる取得元の解決順序が必要だったためである。[保存時の補正では遅いケース](./100-source-rename-before-checkpoint-lookup.md)で説明する。

## 学んだこと

**INFERENCE:** 取得経路と保存上の同一性を分離すると、経路変更後も既存記事をチェックポイントとして使いやすい。ただし、元のキーをアーカイブ側のキーから正しく対応付けることが前提になる。

## 制約・次の課題

今回は明示的に選択した対象の手動補完であり、定期取得の対象拡張ではない。名前照合が曖昧な移行は自動で解決しない。一覧に載らない記事の存在までは、集合の一致だけでは確認できない。
