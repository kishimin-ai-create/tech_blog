# 公開サイトの画像生成を、ダウンロード成功と画素の両方で確認する

## はじめに

Mojicaの絵文字修正を確認した際、PNGのダウンロードが成功しても、中身が欠落グリフのままという結果が出た。2026年10月22日の再検証では、公開サイトから取得した12枚の絵文字画像を、検証済みのローカルイメージが生成した参照画像と比較した。

この記事では、画像生成機能のリリース確認で、通信・ダウンロード・描画内容を分けて観測する方法を扱う。ビルドと稼働コンテナの区別は[既存記事](./143-apply-verified-uv-image-without-recreating-db.md)で扱っている。

## 確認したかったこと

対象は[公開Mojica](https://mojica.pages.dev/)の実フロントエンドと実APIだった。APIモックを使わず、既存のPlaywrightのページ操作とテスト基盤をLinuxコンテナで利用した。ブラウザーはGoogle Chrome、workerは1、retryは0とした。

修正済みのローカルイメージがあっても、公開側で同じ描画ができるかは別途確認する必要があった。

## テスト条件を分ける

日本語・英語の2言語、通常画像・X背景・Xアイコンの3種類を、次の3入力群で試した。枠は`KA`、絵文字ケースの外側は空白とした。

| 入力群 | 内側 | ケース数 |
| --- | --- | ---: |
| 通常文字 | A（外側はB） | 6 |
| 単一の絵文字 | 😀 | 6 |
| 複数・結合絵文字 | 😀🚀👩‍🚀🇯🇵 | 6 |

送信前にダウンロード待機を開始し、画面から生成を要求した。保存名の型別接頭辞、PNGのシグネチャ、画像のデコードを確認し、動画・スクリーンショット・traceも保存した。

## 最初の検証で分かった限界

初回は通常文字6件が成功したが、複数絵文字の通常画像は日本語・英語ともHTTP 422、`IMAGE_SIZE_LIMIT_EXCEEDED`だった。プロフィール系はPNGを取得できても、絵文字が欠落グリフになっていた。単一絵文字の6件もダウンロード自体は成功し、中身の描画問題が残った。

ダウンロードの待機だけでは、既に表示されたAPIエラーがタイムアウトとして見えてしまう。後続の一時検証テストでは、ダウンロードと画面上のエラー表示を競合させ、どちらが起きたかを記録した。これは検証用ファイルでの工夫であり、製品のE2Eテストを恒久的に変更したわけではない。

## 参照画像と比較する

再検証でダウンロードできた12枚を、ローカルの`glyph-forge:1.0.5`で同じ入力・設定から生成した参照画像と照合した。参照は入力2群×画像3種類の6枚で、日本語・英語それぞれの出力と比較する。

比較ではPNGファイル全体のバイト列ではなく、デコード後のRGBA画素と寸法を使った。PNGのメタデータや圧縮表現の差と、描画内容の差を分けるためである。参照側も同じ不具合を持つ可能性があるため、顔・ロケット・宇宙飛行士・日本国旗を識別できるか、代表画像も目視した。

## 実際の結果

最終実行は18 passed、0 failed、0 skipped、0 flaky、約2.3分だった。traceのネットワーク記録から、18件の生成POSTがすべてHTTP 200だったことも確認した。

| 確認対象 | 観測結果 |
| --- | --- |
| 2言語×3種類×3入力群 | 18件すべて成功 |
| 絵文字画像の参照比較 | 12枚すべて寸法・RGBA画素が一致 |
| 通常文字の通常画像 | 800×400 |
| 絵文字の通常画像 | 1080×540 |
| X背景・Xアイコン | 1500×500・400×400 |
| 前回422だった複数絵文字の通常画像 | 両言語でHTTP 200 |

フォントの計測値が異なるため、通常画像の寸法を文字種にかかわらず800×400と固定する検証にはしなかった。最終実行では欠落グリフを再現せず、ローカルの修正済み描画と一致した。

## この結果から言える範囲

確認できたのは、テストした入力で公開サイトが修正済みと同じ描画を返すことまでである。公開側の稼働イメージdigestは独立に取得していないため、画素一致だけから配備済みdigestを断定しない。検証のためのデプロイ操作も行っていない。

別ブラウザー、モバイル、負荷、Unicode全体は未検証である。画素の厳密一致は参照側のフォント・描画依存・設定を揃えられる条件で有効だが、異なる描画環境を比較する際は差の意味を再評価する必要がある。
