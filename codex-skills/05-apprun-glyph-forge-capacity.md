# AppRunとGlyph Forgeの容量設定を分けて考える

## 結論

AppRunの最大インスタンス数と、Glyph Forgeプロセス内の同時処理数は別の制御である。AppRunの最大スケール数を4にしても、最小スケール数が0でスケール目安に届かなければ、1インスタンスへリクエストが集中する。画像生成のようなCPU負荷の高い処理では、1コンテナ1処理を維持し、コンテナを複数起動する構成が安全な初期値になる。

## 前提条件

今回のリリースE2Eでは、5 browser projectsを5 workersで実行し、1回のテストで5件の画像生成が同時に始まる。AppRunは共用型、Glyph ForgeはDockerコンテナとして稼働する。

## 設定の役割

| 設定 | 制御対象 | 現在の意味 |
| --- | --- | --- |
| AppRun最小スケール数 | 常時起動するコンテナ数 | 0ならコールドスタートする |
| AppRun最大スケール数 | 起動可能なコンテナ数 | 4でも常に4ではない |
| AppRun同時リクエスト目安 | スケールアウトの目安 | 小さい値ほどスケールしやすいが、設定範囲に制約がある |
| Glyph Forge同時処理数 | 1コンテナ内の画像生成数 | 現在は1件 |
| Glyph Forge待機キュー | 1コンテナ内の待機数 | 現在は9件 |

AppRunの最大値は上限であり、受信した5件を必ず5コンテナへ割り当てる保証ではない。最小値0の場合、最初のバーストは起動中の少数インスタンスへ集中しやすい。

## 検証

5 workersで実行したリリースE2Eでは、次のようにダウンロードイベントが30秒以内に発生しない失敗が確認された。

```text
Running 30 tests using 5 workers
5 failed
25 did not run
```

一方、1 workerでは30件が成功した。これはGlyph Forgeの同時処理数1でも、直列なら処理できることを示すが、同時利用時の余裕を示すものではない。

## 推奨構成

5件程度の同時処理を安定させる初期構成は次の通りである。

```text
Mojica API: 1インスタンス
Glyph Forge: 最小4・最大4インスタンス
Glyph Forge各インスタンス: 同時処理1件
```

この構成では、各Glyph Forgeコンテナが1件ずつ処理し、AppRunのロードバランサーがリクエストを分散する。常時4インスタンスを維持する料金と、コールドスタートを許容して最小1〜最大4にする遅延を比較して選択する。

別案として、Glyph Forgeの同時処理数を2以上へ増やす方法もある。ただし、画像生成はCPU・メモリを消費するため、CPU使用率、メモリ、生成時間、503件数を計測してから変更する。

## 残存リスク

最小スケール数を増やしても、AppRunの起動遅延やGlyph Forgeの生成時間がなくなるわけではない。Mojica APIのタイムアウト、Glyph Forgeのキュー待機時間、Playwrightのテストタイムアウトは、同じ最悪値を前提に設定する必要がある。

## まとめ

* AppRunの最大スケール数は、実際の同時処理インスタンス数ではない。
* Glyph Forgeの同時処理1件は、1コンテナを保護する安全側の設定として妥当である。
* 同時利用を増やす場合は、まず複数コンテナ化し、その後にプロセス内並列度を負荷試験で評価する。
