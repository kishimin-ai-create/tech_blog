# response.textを渡すとJSONのmessageが消えた理由

## 結論

`response.text`は本文ではなく関数である。`c.json({ message: response.text }, 422)`では関数をJSONへ変換することになり、今回の検証では本文が`{}`になった。`await response.text()`で実際に本文を読む必要がある。

## 発生した問題

上流の失敗時にHTTP 422・500を返す分岐を追加した直後、コードでは`message`に`response.text`そのものを渡していた。ステータスの分岐は機能しても、エラーの説明が返らなかった。

## 調査

fetchをモックに置き換え、上流からJSONエラーを返してHonoルートを呼んだ。

| 上流 | Honoのステータス | Honoの本文 |
| --- | --- | --- |
| 422 | 422 | {} |
| 500 | 500 | {} |

ステータスとContent-Typeだけなら見逃すが、返却JSONのキーを確認すると問題が分かった。

## 原因

メソッドを呼ばずに参照していた。

```ts
// 変更前
return c.json({ message: response.text }, 422);

// 変更後
return c.json({ message: await response.text() }, 422);
```

関数値を含むオブジェクトをJSON化しても、その値は文字列の本文にはならない。メソッドを呼ぶことと、返るPromiseを待つことの両方が必要になる。

## 解決方法

ユーザーによる修正後、コードが`await response.text()`になったことを確認した。この変更は上流エラーの分岐と一緒にコミット`d5f6a04`へ入っている。

## 動作確認

本文を`upstream failure`としたモックを用意し、422・500・503の各ケースで、返却JSONの`message`が同じ文字列になることを確認した。

`text()`は文字列を返すので、上流本文がJSONでも構造化されたオブジェクトとして取り出すわけではない。この実装は上流エラー形式の正規化までは行っていない。

## 再発防止

提案として、HTTPステータスとContent-Typeに加えて、エラー本文の値までassertする。今回の確認は一時的なスクリプトであり、回帰テストファイルへの追加は未実施である。

## まとめ

「エラーを返す分岐がある」だけでは、意味のある説明を返しているとは限らない。呼び忘れとawait漏れを分け、返却本文そのものを確認する。

## 根拠

2026年10月18日のローカル差分、修正前の422・500で本文{}となったモック結果、修正後のモック結果、コミット`d5f6a04`。
