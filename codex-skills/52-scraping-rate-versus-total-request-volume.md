# スクレイピングの負荷は間隔だけでなく総リクエスト数で評価する

## はじめに

公開ページの履歴をバックフィルしたところ、3〜4秒の待ち時間を入れた逐次処理でも数時間かかりました。短時間のアクセス頻度は低くても、既存データの再確認を含む総リクエスト数が大きければ、実行時間と相手側への累積負荷は増えます。

この記事では、アクセス間隔と総量を分けて評価した結果をまとめます。取得元を特定できるURL、名称、HTML構造は扱いません。

## 背景

収集処理は、各HTTPリクエストの前に基本3秒と最大1秒のランダムな待ち時間を入れます。並列アクセスは行わず、1件ずつ順番に取得します。

```text
待ち時間 = 3秒 + 0〜1秒のランダム値
```

この条件では、応答時間を除いた理論上限は約15〜20リクエスト/分です。

## 実際に確認した結果

バックフィル後のDBを確認すると、記事数は4,348件から7,865件へ増えていました。新規保存は3,517件です。

| 項目 | 確認値 |
| --- | ---: |
| 実行前の記事数 | 4,348件 |
| 実行後の記事数 | 7,865件 |
| 新規保存数 | 3,517件 |
| 関連アセット情報 | 40,410件 |

アセット情報はHTML内のURLをDBへ保存した件数であり、画像本体を40,410回取得したことを意味しません。

一方、バックフィルは新規記事だけでなく、既存記事の詳細ページも再取得して重複を確認します。そのため、HTTPリクエスト数は新規保存数より大きくなります。

## 良かったこと

- HTTPアクセスは逐次実行で、同時リクエストを発生させない。
- 各リクエスト前に待ち時間がある。
- 画像本体を収集せず、記事HTMLに含まれる参照情報だけを保存する。
- `429`とサーバーエラーを一時的な失敗として扱う。

## うまくいかなかったこと

- 既存記事の詳細ページも再取得するため、再実行の通信量が大きい。
- `429`応答時に`Retry-After`を解釈しない。
- 再試行は最大3回だが、指数バックオフを使用しない。
- 実行結果を永続的なジョブ履歴へ保存しないため、終了コードを後からDBだけで確認できない。

## 学んだこと

「3〜4秒待っているから負荷が小さい」とは断定できません。運用時には次の値を分けて確認する必要があります。

1. 同時実行数
2. 1分あたりのリクエスト数
3. 1回の実行における総リクエスト数
4. 同じページを再取得する回数
5. `429`や`5xx`発生時の停止・再試行方法

利用規約、robots.txt、管理者の許可も、技術的な待ち時間とは別の確認事項です。

## 次回どうするか

PROPOSALとして、初回バックフィルでは5〜8秒程度の間隔を候補とし、15〜30分で処理を区切ります。また、既存記事を一覧上の識別子で判定し、不要な詳細ページ取得を避ける設計を検討します。

これらは本記事執筆時点では未実装です。

## まとめ

短時間のアクセス頻度だけを見ると、今回の逐次処理は高頻度ではありません。しかし、数時間にわたって既存記事を再取得すると総量は大きくなります。スクレイピングの負荷は、待ち時間だけでなく総リクエスト数と再取得量を含めて評価する必要があります。
