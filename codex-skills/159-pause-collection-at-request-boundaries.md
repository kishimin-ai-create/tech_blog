# 収集処理をメンテナンスで止めるとき、次のHTTP要求の前で停止する

## 結論

slope-collectorでは、実行中のHTTP要求と、取得を完了した記事の保存を終えてから止める設計を選んだ。停止状態は次の要求の直前に読み直す。対象は、外部サイトから記事を順番に取得する同期的なコレクターである。

2026年10月24日にWindows・Python 3.14.7でローカル検証した。GUIと本番デプロイは今回の対象に含めていない。

## 背景と解決したい課題

公式サイトやアーカイブがメンテナンス中だと分かっている場合、通常の収集を続けても取得できず、再試行や失敗通知が増える。そこで、公式とアーカイブを収集元ごとに停止できるようにした。

ただし、停止を押した瞬間にプロセスを終了すると、進行中の処理をどこまで終えられたか扱いにくい。今回は「停止した後に追加の要求を始めないこと」と「保存できる記事を保持すること」を両立させた。

## 前提・制約

- 日次収集と手動バックフィルの両方に停止を適用する。
- 取得済み記事は記事単位のトランザクションで保存する。
- 他の収集元を巻き込まず、対象の収集ルートを止める。
- リクエスト間隔の待機、通信エラーの再試行、リダイレクトがある。

## 検討した選択肢

### Option A：収集全体の完了後に停止する

進行中の処理を最後まで完了させる。実装上の停止点は少ないが、メンテナンス中にも残りの記事への要求が続く。

### Option B：要求と記事保存の区切りで停止する

進行中の要求と保存を終え、次の要求を送らない。停止状態を複数の要求経路で読み直す必要があるが、停止操作後の通信を抑える目的に合う。今回はこの案を選んだ。

| 評価軸 | 全体完了後 | 要求の区切り |
| --- | --- | --- |
| 進行中の記事の保存 | 完了できる | 完了できる |
| 残りの記事への要求 | 続く | 次の要求前に止める |
| 停止確認の場所 | 実行開始付近 | 要求経路ごとに必要 |

## なぜ要求の直前に確認するのか

実行開始時だけの確認では、開始後にGUIから停止した場合を扱えない。待機前の確認だけでも、待機中に入った停止を見落とす。実装では初期処理前と要求前に状態を確認し、HTTPクライアントにも確認処理を注入した。

構造を示す抜粋は次のとおり。`before_request()`は、共有DBで停止を確認すると`CollectionPausedError`を送出する。

```python
def get_html(path: str) -> str:
    before_request()
    wait_before_request(settings, path, sleep=sleep, random_value=random_value)
    return client.get_html(path)
```

HTTPクライアント側でも実際の送信前に確認するため、待機後とリダイレクト先への要求にも適用される。この例は構造の抜粋で、単独で実行するコードではない。

## 実装後の結果

`test_collection_pause.py`では、停止のタイミングを開始前、一覧応答中、記事応答中、再試行前、待機中、リダイレクト前に分けて確認した。記事応答中に停止したケースでは1記事を保存し、次の記事にはアクセスしなかった。日次収集とバックフィルの両モードで確認している。

アーカイブについても同様の境界を検証した。停止自体は収集失敗にせず、結果の`paused_sites`へ対象を記録する。

## トレードオフ・今後の懸念

これは協調的な停止であり、送信済みの要求を取り消す機能ではない。待機も中断せず、終了後の確認で次の送信を防ぐ。APIの`paused`は要求された状態を示し、プロセスが停止点へ到達済みであることまでは表さない。

HTTPはモックで検証した。実サイトのメンテナンス時の挙動や本番環境の応答時間は測定していない。
