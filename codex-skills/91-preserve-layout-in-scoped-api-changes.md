# API変更で依頼されていない構造変更を戻した記録

## はじめに

APIのURL分離に伴い、ルートファイルの新設と画像保存処理の変更を追加した。しかし利用者はその変更を求めておらず、既存の構造と処理へ戻すよう指示した。この記事は、機能変更の依頼範囲を確認するための振り返りである。

## 背景と目的

当初の依頼は画像生成の2つのURLとコミットの粒度だった。ファイルを分割する合意や、保存処理をcontext managerへ変更する合意は確認できなかった。

## 実際にやったこと

FACT: `f227d9a` で新設したルートモジュールを取り除き、ハンドラを既存の `services/analysis/analyze.py` へ戻した。公開URLは維持した。

FACT: `9fee032` で生成済み画像の保存部分を次の以前の形へ戻した。

```python
image = Image.open(file_path)
image.save(file_path)
```

アップロード画像のデコードで既に使われていたcontext managerは別の箇所であり、この復元と混同しない。

## うまくいかなかったこと

要求された機能に加え、依頼されていない配置変更と保存処理の変更を行った。そのため、機能実装後に復元コミットが必要になった。一般的な改善案として妥当かどうかと、その依頼で変更する権限があるかどうかを分けて扱えていなかった。

## 実際の結果

両ハンドラは既存モジュールに置かれ、生成済み画像の保存処理は元の形になった。これは復元の結果であり、応答後に生成ファイルを削除するレビュー指摘への修正ではない。

## 学んだこと

INFERENCE: URLの分離を依頼されたとき、モジュール配置の変更まで必要とは限らない。PROPOSAL: 構造変更や局所的なリファクタリングが依頼の目的に必要かを差分ごとに確認し、必要性を説明できないものは追加しない。

## 制約

この記録は既存構造を永続的に固定する設計決定ではない。将来どの条件で構造変更を認めるかは合意されていない。ADR化するなら、適用範囲と例外の確認が必要である。
