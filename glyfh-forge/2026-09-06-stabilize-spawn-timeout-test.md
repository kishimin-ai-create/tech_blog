# Windows spawnでワーカータイムアウトテストが不安定になる原因と解決方法

## 結論

`multiprocessing`の`spawn`を使うテストで0.5秒のタイムアウトを設定すると、Windowsでは処理本体が始まる前に期限切れになることがある。処理開始後の強制終了を検証したい場合は、子プロセスが起動できる猶予と、必ずタイムアウトする十分長い処理時間を分けて設定する。

今回のテストでは、処理時間を2秒から5秒、タイムアウトを0.5秒から2秒へ変更した。本番の30秒タイムアウトと停止処理は変更していない。

## 発生した問題

### 症状

全テストを標準順序で実行すると、タイムアウト自体は発生するものの、子プロセスが書くはずの開始ファイルが存在しないことがあった。

```text
assert started_path.exists()
AssertionError: assert False
```

同じ失敗はカバレッジ付き実行でも再現した。

### 発生条件

- Environment: Windows、Python 3.12.4
- Process start method: `multiprocessing.get_context("spawn")`
- Test timeout: 0.5秒
- Worker operation: 開始ファイルを書いた後、2秒待機して完了ファイルを書く

### 影響

ワーカーの停止処理とは独立したプロセス起動時間によって、全体テストとカバレッジ取得が不安定になった。タイムアウト例外だけを見ると成功しているように見えるが、開始ファイルがないため「開始済み処理を停止した」というテストの前提を満たしていなかった。

## 調査

### 仮説1：ワーカー停止処理が開始ファイルを削除している

実装を確認すると、停止処理は子プロセスに対して`terminate()`、`join()`、必要なら`kill()`を呼ぶだけで、開始ファイルを削除していなかった。この仮説は実装と一致しなかった。

### 仮説2：子プロセスが処理本体へ到達する前にタイムアウトしている

親プロセスは次の順序で処理する。

```python
process.start()
if not parent_connection.poll(timeout_seconds):
    raise ImageGenerationTimeout
```

`spawn`では、新しいPythonプロセスの起動とモジュールの読み込みを経てから対象関数が実行される。0.5秒はその起動時間も含むため、負荷によっては開始ファイルが書かれる前に`poll()`が期限切れになる。

実際に、タイムアウト例外は期待どおり発生している一方、開始ファイルだけが存在しないという結果だった。この観測は仮説2と一致した。

## 原因

テストが「子プロセスは0.5秒以内に起動して処理本体へ到達する」と暗黙に仮定していたことが原因だった。

本番コードのタイムアウトはプロセス起動後の結果待ち全体へ適用されるため、起動前に期限切れになること自体は契約違反ではない。しかしテストの目的は、開始済みの処理がタイムアウト後に完了側の副作用を起こさないことだった。0.5秒では、その状態まで到達したことを保証できなかった。

## 解決方法

子プロセスが開始できる猶予を持たせつつ、処理本体は確実に期限を超える値へ変更した。

```python
def _write_after_delay(started_path: str, completed_path: str) -> Image.Image:
    Path(started_path).write_text("started", encoding="utf-8")
    time.sleep(5)
    Path(completed_path).write_text("completed", encoding="utf-8")
    return Image.new("RGB", (1, 1), (255, 255, 255))


with pytest.raises(ImageGenerationTimeout):
    run_image_generation_in_process(
        _write_after_delay,
        (str(started_path), str(completed_path)),
        {},
        2,
    )
```

2秒は子プロセスの起動猶予、5秒はタイムアウト後まで実行が続くはずの処理時間という別の役割を持つ。開始ファイルの存在と完了ファイルの不在を確認することで、開始済みワーカーが途中で停止されたことを検証する。

## 動作確認

対象テストを独立したPythonプロセスで3回連続実行し、すべて成功した。その後、標準順序の全116テストとカバレッジ付き全テストも成功した。

## 再発防止

- プロセス起動時間と、検証対象となる処理時間を同じ短いタイムアウトへ押し込まない。
- タイムアウト例外だけでなく、処理開始と後続副作用の有無を観測する。
- 本番値とテスト値を混同せず、テスト用の値が何を保証するかコメントで残す。
- 全体実行とカバレッジ付き実行でも確認し、単体実行だけで安定したと判断しない。

## まとめ

- 症状: Windowsで開始ファイルが作られず、ワーカー停止テストが失敗した。
- 原因: 0.5秒の期限が`spawn`の起動時間まで含み、処理本体へ到達できなかった。
- 解決方法: 起動猶予を2秒、処理時間を5秒に分離した。
- 教訓: タイムアウトテストでは「期限切れになった」だけでなく、「検証対象の状態へ到達してから期限切れになった」ことを確認する。
