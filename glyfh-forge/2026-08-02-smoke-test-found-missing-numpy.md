# コンテナのスモークテストがNumPy不足を見つけた

Dockerイメージがビルドできることと、アプリケーションが動くことは別である。Glyph Forgeの本番コンテナは最初のパッケージング後、画像生成に必要なNumPyが本番依存から漏れていることが分かった。

## なぜテスト環境では見つからなかったのか

開発用の`requirements.txt`にはNumPyが含まれている。普段の仮想環境ではすでにインストール済みなので、ユニットテストやAPIテストは通る。

一方、本番イメージは`requirements-prod.txt`だけを使う。依存を分離したことで、開発環境が暗黙に補っていた不足がコンテナ内で表面化した。

Glyph Forgeの画像処理は、画像から二値グリッドへ変換する処理などでNumPyを使う。FastAPI、Uvicorn、PillowだけではAPIプロセスを起動できても、実際のレンダリング経路を完走できない。

## `/health`だけでは不十分

`GET /health`はプロセスの起動確認に有効だが、画像レンダラーの依存までは通らない。今回のような不足を見つけるには、コンテナを起動して`POST /images`からPNGを生成するスモークテストが必要になる。

確認の段階を分けると、役割が明確になる。

1. イメージをビルドできる
2. コンテナが非rootで起動する
3. `/health`が`200`を返す
4. `/images`がPNGを返す

四段目まで通して初めて、主要な実行経路の依存が揃っていると判断できる。

## 依存リストもテストで固定する

修正では`numpy==1.26.4`を`requirements-prod.txt`へ追加し、コンテナ設定テストの期待値も更新した。これにより、将来の整理でNumPyだけが再び本番依存から消えれば、設定テストが差分を知らせる。

本番依存を最小化する作業では、依存を減らすこと自体を成功条件にしない方がよい。実際の主要機能をスモークテストし、「小さいが動かないイメージ」になっていないことを確かめる必要がある。
