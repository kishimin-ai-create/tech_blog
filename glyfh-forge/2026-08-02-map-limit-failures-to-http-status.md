# 公開APIの制限をHTTPステータスへ写像する

## はじめに

入力や負荷に複数の制限を設けると、失敗をすべて同じエラーにしたくなる。しかしクライアントが修正すべき問題と、時間を置いて再試行すべき問題では意味が違う。

Glyph Forgeでは、画像生成APIの失敗を次のように整理した。

| 状況 | ステータス |
| --- | --- |
| 文字列、フォント、色、画像寸法、実画像形式が不正 | `422 Unprocessable Entity` |
| multipart本文が上限超過 | `413 Content Too Large` |
| IP単位の呼び出し頻度が超過 | `429 Too Many Requests` |
| 同時実行枠、待機枠、生成時間が超過 | `503 Service Unavailable` |

## `422`は入力を直せる場合

文字列が長すぎる、両方の塗り文字列が空白だけ、フォントサイズが範囲外、アップロード画像が未対応形式、といった問題は同じ入力で再試行しても成功しない。クライアント側で値を修正する必要がある。

子プロセス内のレンダラーが`ValueError`を返した場合も、親側で意味を保ったまま`422`へ変換する。

## `413`は解析前に返す

multipart本文の上限超過は、フィールドの意味を検証する前にHTTP本文そのものが大きすぎる状態である。そのため`413`として区別する。早い段階で拒否することが、ステータスの意味と資源保護の両方に効く。

## `429`と`503`は再試行可能性を伝える

レート超過はクライアント単位なので`429`、サーバーの現在容量が利用できない場合は`503`とした。どちらも`Retry-After`を返し、即座の連続再試行を避けられるようにする。

生成タイムアウトも、入力が必ず不正とは限らないため現在は`503`へ写像している。ただし何度も同じ入力で期限を超えるなら、運用メトリクスをもとに入力上限や処理設計を見直す必要がある。

エラー設計は例外クラスをHTTP番号へ置き換えるだけではない。「誰が、どうすれば次に成功できるか」を応答へ表す作業である。
