# 直列処理APIのバースト容量に余裕を持たせた理由

## 結論

CPU負荷の高い処理を1件ずつ実行するAPIでは、クライアントの並列数と同じ容量を設定するだけでは、次の要求群との重なりで不安定になり得る。今回のglyph-forgeでは、5並列の呼び出しに対して、実行1件と待機9件の合計10件を受け付ける設計へ変更した。

ただし、これは10件を同時に処理する保証ではない。画像生成は直列のままであり、10件を有限時間だけ待たせられるというバースト耐性の契約である。

## 背景

glyph-forgeは、Mojica APIから呼び出される画像生成サービスである。IPベースのレート制限を内部APIから削除した後も、CPUとメモリを守るため、同時実行数、待機キュー、タイムアウト、リクエストサイズ制限を残していた。

変更前の容量は次のとおりだった。

```python
MAX_CONCURRENT_IMAGE_REQUESTS = 1
MAX_WAITING_IMAGE_REQUESTS = 4
IMAGE_REQUEST_QUEUE_TIMEOUT_SECONDS = 10.0
IMAGE_GENERATION_TIMEOUT_SECONDS = 30.0
```

合計容量は5件であり、MojicaのPlaywrightが5ブラウザーを並行実行すると上限にちょうど一致する。上限と通常の並列数が同じため、ブラウザーごとの処理時間差によって次のテストが重なる余地がなかった。

## 解決したい課題

通常速度の正当な10件同時要求を、IPレート制限による`429 Too Many Requests`や、容量不足による`503 Service Unavailable`にせず受理する。一方で、無制限な待機や画像生成プロセスの大量並列化は導入しない。

## 前提・制約

- 画像生成はCPUとメモリを消費する。
- 1アプリケーションプロセスあたりの画像生成は同時1件を維持する。
- 待機数と待機時間には上限を設ける。
- 容量不足では`503`と`Retry-After`を返す。
- 個々の画像生成は30秒で打ち切る。
- 今回は複数インスタンスや永続ジョブキューへ移行しない。

## 検討した選択肢

### Option A：合計5件の容量を維持する

#### メリット

- 待機要求が少なく、メモリ使用量と待ち時間を小さく抑えやすい。
- 設定変更が不要である。

#### デメリット

- 5並列と容量上限が一致し、要求群が少し重なるだけで503になり得る。
- E2Eの実行タイミングに対する余裕がない。

### Option B：直列処理を維持し、合計10件まで待機可能にする

#### メリット

- 画像生成プロセスを同時に増やさず、5並列の2バッチ分を受け付けられる。
- 上限を超えた要求を503で拒否する保護を維持できる。

#### デメリット

- 後続要求の待ち時間が長くなる。
- 処理能力そのものは増えない。

### Option C：複数workerまたは複数インスタンスで並列処理する

#### メリット

- 十分なCPUとメモリがあれば、画像生成のスループットを増やせる。
- 単一プロセス障害への耐性を高められる可能性がある。

#### デメリット

- CPU、メモリ、運用コストが増える。
- アプリ内の容量制限がworkerごとに分かれる場合、インスタンス全体の上限を別途設計する必要がある。

## 評価軸

| 評価軸 | Option A | Option B | Option C |
| --- | --- | --- | --- |
| 5並列への余裕 | なし | 10件まで受付 | 構成次第 |
| CPU並列度 | 1 | 1 | 増加 |
| 待機の有界性 | 維持 | 維持 | 構成次第 |
| 運用コスト | 変更なし | 小さい | 大きい |
| スループット向上 | なし | なし | 見込めるが未計測 |

## 最終判断

Option Bを採用し、設定を次の値へ変更した。

```python
MAX_CONCURRENT_IMAGE_REQUESTS = 1
MAX_WAITING_IMAGE_REQUESTS = 9
IMAGE_REQUEST_QUEUE_TIMEOUT_SECONDS = 30.0
IMAGE_GENERATION_TIMEOUT_SECONDS = 30.0
```

## なぜこの選択をしたか

目的は、単一インスタンスの処理能力を未計測のまま増やすことではなく、5並列の境界値依存をなくすことだった。実行数を1件に保てば、高コストな子プロセスを無計画に増やさずに済む。待機枠を9件へ増やすことで、1件実行中でも残り9件をキューへ入れられる。

Uvicornには複数workerと`--limit-concurrency`がある。ただし、Uvicornの同時接続制限は上限到達時に503を返し、要求をアプリケーションの処理待ちキューへ入れる機能ではない。今回必要だったのは、画像生成だけに適用する有界な待機だったため、既存のアプリケーション側制限を拡張した。

## 実装後の結果

10スレッドをBarrierで同時開始するAPI回帰テストを追加した。変更前は一部の応答が503となり、変更後は10件すべてが200になった。

テスト内の画像生成は0.1秒の遅延を持つスタブであり、本番レンダリングの性能測定ではない。このテストが証明するのは、通常速度の処理に対して10件分の受付容量があることまでである。

```text
10件同時回帰テストを5回連続実行: pass
全テスト: 116件 pass
総合カバレッジ: 90%
```

`autoflake`、`isort`、`black`、`flake8`、`mypy src`も成功した。

## トレードオフ・今後の懸念

10件受付は10件同時処理や一定の応答時間を保証しない。先行処理の合計時間がキュー待機上限へ達すれば、容量内に見える要求でも503になり得る。

継続的な要求が増えた場合は、待機枠をさらに広げる前に、生成時間のp95とp99、CPU、ピークメモリ、503発生率を測る必要がある。その結果に基づいて、複数インスタンスまたは永続ジョブキューを選択する。

## まとめ

並列数と容量上限を同じ値にすると、正常なタイミングの揺らぎを吸収できない。今回の条件では、画像生成の直列実行と503保護を維持しながら、5並列に対して合計10件の受付枠を持たせた。

重要なのは、キュー容量をスループット保証と混同しないことである。費用をかけた水平スケールは、実測値が単一インスタンスの限界を示してから判断する。
