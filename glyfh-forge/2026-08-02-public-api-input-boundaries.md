# 一般公開する画像生成APIの入力境界を決める

画像生成APIを一般公開するなら、入力欄を「文字列だから安全」と考えることはできない。文字数、空白、制御文字、正規化、数値範囲が曖昧なままだと、処理時間や出力サイズが利用者の入力だけで大きく変わるからだ。

Glyph Forgeでは、公開APIの入力を次の範囲へ絞った。

| 項目 | 制限 |
| --- | --- |
| `frame_text` | 1〜64文字 |
| `inner_text` | 1〜128文字 |
| `outer_text` | 1〜128文字 |
| `frame_font_size` | 8〜128 |
| `output_font_size` | 10〜64 |
| RGB各成分 | 0〜255 |

## 空白を一律禁止しなかった理由

`frame_text`は画像の形を決めるため、空白だけでは意味のあるフレームを作れない。そのため、少なくとも1つの可視文字を必須にした。

一方、`inner_text`と`outer_text`は塗り分けに使う。片方を空白だけにすれば、フレームの内側または外側を文字で埋めない表現ができる。そこで片方だけの空白文字列は許可し、両方が空白だけの場合は拒否する関係制約にした。

個々のフィールドだけを見るバリデーションでは、この条件を表せない。Pydanticのフィールド検証で各文字列を整えた後、モデル全体の検証で2項目の組み合わせを確認している。

## Unicodeは数える前に正規化する

見た目が同じ文字でも、Unicode上は複数の表現を持つ場合がある。Glyph ForgeではNFC正規化を先に行い、その結果に対して長さを検証する。

これにより、結合文字を使った表現と合成済み文字で、同じ見た目なのに文字数判定だけが不自然に変わる問題を減らせる。改行、タブ、NULLなどUnicodeカテゴリが`Cc`の制御文字も拒否する。

## 未知のフィールドも拒否する

リクエストモデルには`extra="forbid"`を設定した。廃止した入力項目をクライアントが送り続けても、黙って無視せず`422 Unprocessable Entity`で知らせるためだ。

一般公開APIの入力制限は、単に最大値を並べる作業ではない。どの表現を残したいか、複数フィールドの関係をどう扱うか、互換性のない旧入力をどう検出するかまで決めて、初めて境界になる。
