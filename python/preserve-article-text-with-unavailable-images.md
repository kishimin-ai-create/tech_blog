# 取得できない画像URLが記事本文まで失敗させた原因と対処

## 結論

記事本文の解析失敗は、画像URLの二種類の扱いが原因だった。収集元自身のHTTPSホストが画像の許可境界から漏れていたため、許可集合へ加えた。ブラウザ内だけで有効な`blob:` URLは後から取得できないため、画像アセットと保存本文から除いた。本文の文章は保存する。

## 発生した問題

### 症状

対象を指定した全件取得で、一部の記事の解析が失敗し、文章も保存されなかった。失敗した詳細を調べると、収集元自身のHTTPS画像と`blob:`画像が含まれていた。

### 発生条件と影響

PythonのHTML解析処理が記事本文内の画像をアセットとして抽出し、保存用HTMLもサニタイズする構成だった。どちらの経路でも許可外のURLを拒否するため、一つの画像URLが記事全体の失敗へつながった。

## 調査

解析コードの`_assets()`と`_sanitize_body()`を確認し、画像のURLが`_asset_path()`を通ることを追った。修正前の許可集合はCDNホストに寄っており、収集元自身のホストは画像の取得先として認められていなかった。また、`blob:`はブラウザの一時的な参照で、収集処理から後でHTTP取得できるURLではない。

## 原因

HTMLに現れる画像をすべて「保存可能な外部アセット」として扱っていたことが原因だった。収集元自身の通常のHTTPS画像まで拒否し、`blob:`を通常のURLとして検証すると失敗する。結果として、画像だけの問題が本文全体の解析失敗へ広がった。

## 解決方法

画像の相対パス化に使う許可ホストへ、収集元自身のホストを含めた。`blob:`画像はアセット生成時にスキップし、保存用HTMLからも`img`要素を除く。未承認の外部ホストは許可しない。

```python
if urlsplit(source).scheme == "blob":
    continue
```

この分岐は画像アセット用である。保存用HTMLでも同じスキームの画像を除くため、取得不能な参照が本文に残らない。残った画像には、許可ホストとHTTPSの検査が適用される。

## 動作確認

テスト用HTMLには通常の文章、収集元自身のHTTPS画像、`blob:`画像を一緒に置いた。テストは文章と通常画像が残り、`blob:`が保存用HTMLとアセット一覧の両方から消えることを確認した。対象指定のローカル再収集では、以前失敗した未取得の記事を保存し、失敗件数は0だった。

## 再発防止と制約

画像URLの種類を本文の成否と切り離してテストする。本文を保つために許可ホストを無制限に広げることはしない。今回の処理は`blob:`画像自体を復元しないため、その画像を保存する必要がある用途には別の取得方式が必要になる。

## まとめ

画像URLの失敗を本文の欠落へ波及させないため、取得可能な収集元画像は境界内で扱い、ブラウザ専用画像は除外した。本文とアセットの双方を検証したことが、修正の成立条件だった。

## 根拠

- `app/scraping/adapter.py`の`_assets()`、`_sanitize_body()`、`_asset_path()`
- `tests/small/test_source_adapter.py`の画像を含む記事のテスト
- 対象指定のローカル再収集結果
