# 非アクティブな対象を収集から除く判定位置

## はじめに

収集対象を指定できるバッチと、収集元全体を巡回するバッチでは、対象の状態が分かる時点が違う。この記事は、保存済みの`is_active`を使って不要な要求と保存を防いだ実装を整理する。対象の名前・実データ・収集元は掲載しない。

## 背景と課題

対象を指定する全件取得では、要求を送る前から対象キーが分かる。一方、収集元全体の巡回では、記事の詳細を解析して初めて所属先が確定する。この二つを同じ位置の条件分岐で処理すると、どちらかの経路で不要な要求や保存が残る。

対象状態はローカルDBの`Entity.is_active`にある。未登録の対象を非アクティブと決めつける根拠はないため、明示的に`false`の行だけを除外する。

## 実装

対象指定の経路では、アダプタとHTTPクライアントを使う前に状態を調べる。

```python
if source_entity_key is not None and not repository.is_entity_active(
    config.name, source_entity_key
):
    continue
```

全体巡回の経路では、記事の詳細から対象キーを得た後、保存前に同じ判定を行う。

```python
if not repository.is_entity_active(config.name, record.entity_external_key):
    skipped_records += 1
    continue
repository.persist(record)
```

`is_entity_active()`はDBで該当する状態を読み、`status is not False`を返す。これは、未登録を許可し、保存済みの`false`だけを除くという契約をコードに置いたものだ。既存の記事を削除する処理は含めない。

## 検証と結果

テストでは、対象指定の全件取得で非アクティブな対象へのHTTP要求が0件、訪問ページが0件になることを確認した。全体巡回のテストでは記事を解析した後、保存件数0・スキップ件数1になることを確認した。ローカルの対象指定実行でも、非アクティブな対象への要求は0件だった。

収集元全体の巡回では、対象が確定するまで詳細への要求が必要である。したがって、ここでの「除外」は保存の除外であり、すべての外部要求を事前に消す意味ではない。

## 適用範囲

この判定は収集処理に適用した。全件一覧APIは非アクティブな行も返す契約であり、収集対象の絞り込みと一覧表示を同一視しない。定期収集の増分・直列実行という既存の運用条件も変えていない。

## まとめ

状態を確認できる最も早い位置は実行経路で異なる。対象指定では送信前に、全体巡回では記事解析後かつ保存前に判定する。テストも要求数と保存件数をそれぞれ観測すると、二つの契約を区別できる。

## 根拠

- `app/services/collection.py`の対象指定・全体巡回の分岐
- `app/repositories/collection.py`の`is_entity_active()`
- `tests/medium/test_collection_reliability_integration.py`の二つの収集テスト
