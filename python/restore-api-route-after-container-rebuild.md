# Docker再ビルド後に一覧APIが消えたように見えた原因

## 結論

ローカルコンテナを再ビルドした後に一覧APIが`422`を返した原因は、APIルートのコミットが実行元の`main`に入っていなかったことだった。以前使っていたイメージには、そのコミットを含む別ブランチのコードが入っていた。`main`から復旧ブランチを作り、既存のテストと実装を取り込んで、ローカルAPIと依存する画像生成を再確認した。

## 発生した問題

### 症状

開発用APIの`GET /entities/all`が、再ビルド後に`422`となった。その応答に依存する別サービスの画像生成APIは`500`になった。APIの`/health`は応答していたため、サービス全体が停止した症状ではなかった。

### 発生条件と影響

古いコンテナイメージから、新しいブランチを起点にしたコードでイメージを作り直した後に発生した。開発用の全件一覧を使う分析処理が動かなくなった。

## 調査

`git log`とルート定義を照合した。過去にマージされた機能ブランチへ、マージ完了後に一覧APIのテストと実装が追加されていた。その二つのコミットは当時の`main`に含まれていなかった。新しいイメージのコードでは、`/entities/all`の静的ルートがなく、後続の`/entities/{entity_id}`に当たるため、文字列`all`が数値パラメータとして検証され`422`になることも説明できた。

## 原因

Gitのマージは、マージ時点で到達できるコミットを取り込む。マージ後に同じブランチへ追加したコミットは、自動的には`main`へ入らない。以前のイメージと再ビルド元のコードが異なることを、Docker更新が表面化させた。

## 解決方法

`main`を起点とする復旧ブランチへ、既存の契約テストを取り込んで失敗状態を確認した。その後、ルート実装と開発用API文書を取り込んだ。ルートは数値IDの動的ルートより前に配置し、全件一覧に必要なメタデータと非アクティブな行を返す。

```python
@router.get("/entities/all", response_model=FullEntitiesResponse)
async def list_all_entity_details() -> FullEntitiesResponse:
    ...
```

ここで示す省略記号は説明用であり、そのまま実行するコードではない。実装はDBから全件をID順で取得し、応答モデルに変換する。開発用のローカルAPIという既存の公開範囲は維持した。

## 動作確認

契約テストは実装を取り込む前に`422`で失敗し、実装後に成功した。収集サービスのテスト一式は84件成功、総カバレッジ86.47%で、整形・Lint・型チェックも成功した。ローカルコンテナでは`/entities/all`と`/health`が`200`、依存する画像生成要求がPNGの`200`になった。復旧の変更提案は全チェック成功だが、この記事を作成した時点では未統合である。

## 再発防止

イメージ更新時は、実行中のイメージだけでなく、ビルド元のコミットに必要なルートがあるかを確認する。変更提案のマージ後に同じブランチへ追加した作業は、新しい変更提案で明示的に統合する。これは今回の調査から得た運用上の提案であり、自動検証の追加はまだ行っていない。

## まとめ

APIが「消えた」ように見えたときは、現行コンテナ、ビルド元、`main`の三つのコード状態を区別する。マージ済みのブランチ名だけでは、後続コミットが`main`へ届いた証拠にならない。

## 根拠

- `app/api/records.py`と`tests/small/test_records.py`の全件一覧ルート
- ルートのテスト・実装が追加された順序を示すGit履歴
- ローカルコンテナと分析サービスのHTTP応答、CIのチェック結果
