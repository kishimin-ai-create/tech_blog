# Playwrightで日記CRUDのハッピーパスを守る

## はじめに

日記アプリでは、管理者がログインして日記を作成、編集、削除できる。コンポーネント単体のテストだけでは、ログイン後のページ遷移、フォーム入力、一覧への反映、詳細画面での確認までをまとめて保証しにくい。

## 対象読者

- Next.js の管理画面に E2E テストを追加したい人
- API と UI をまたいだ最低限の本番相当フローを守りたい人
- 秘密情報やデプロイ URL をソースに残さずテストしたい人

## この記事で扱うこと

この記事では、日記アプリの管理画面に対して Playwright の CRUD ハッピーパステストを追加した作業を扱う。

対象は `frontend/e2e/diary-crud.medium.test.ts` と、その周辺の frontend テスト強化である。バックエンド API の実装や認証仕様そのものは扱わない。

## 背景

日記アプリでは、管理者がログインして日記を作成、編集、削除できる。コンポーネント単体のテストだけでは、ログイン後のページ遷移、フォーム入力、一覧への反映、詳細画面での確認までをまとめて保証しにくい。

そこで、管理画面の主要な操作をブラウザレベルで通す E2E テストを追加した。

## 追加したテスト

`frontend/e2e/diary-crud.medium.test.ts` では、次の流れを 1 本のハッピーパスとして確認している。

1. 管理者としてログインする
2. 日記を新規作成する
3. 管理画面の一覧に作成した日記が表示される
4. 日記を編集する
5. 公開側の詳細画面で更新後の内容を読む
6. 管理画面から日記を削除する

テスト用の管理者メールアドレス、パスワード、対象 URL は環境変数から読む。これにより、認証情報やデプロイ URL をコードに固定しない。

## 注意した点

E2E テストは外部環境への依存が大きい。そこで、このテストは `E2E_ADMIN_EMAIL`、`E2E_ADMIN_PASSWORD`、`PLAYWRIGHT_BASE_URL` が揃っていない場合は skip するようにした。

これにより、ローカルの通常テストでは不要な外部通信を避けつつ、必要な環境では実際の CRUD フローを検証できる。

## 周辺の小さな補強

E2E だけでなく、管理画面や認証ストレージ、API プロキシまわりにも小さなテストを追加した。

- `frontend/app/admin/page.small.test.tsx`
- `frontend/app/auth.small.test.tsx`
- `frontend/app/api/proxy.small.test.ts`
- `frontend/next.config.small.test.ts`
- `frontend/app/features/diary/components.small.test.tsx`

E2E で大きな流れを守り、小さな単体テストで条件分岐や境界を守る構成にした。

## まとめ

CRUD のハッピーパスは、画面と API の接続が壊れたときに早く気づける安全網になる。秘密情報を環境変数に逃がし、必要なときだけ実行できる形にしておくと、ローカル開発と本番相当検証の両方で扱いやすい。
