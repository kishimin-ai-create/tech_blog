# GitHub Copilot エージェントライブラリを強化した：FixAgent分割・OWASP ASVS 5.0・エンジニアリング原則56法則

## はじめに

**FixTypeAgent** は「`as any` を使わない」「`@ts-ignore` は最終手段のみ」という厳格なルールを持つ。型エラーは型で直す。ランタイムロジックを変えてはいけない。

## このセッションでやったこと

`.github/` 配下の GitHub Copilot エージェント・スキルライブラリに対して、以下の3つの強化を行った。

1. **FixAgent を6つの専門家エージェントに分割し、FixDispatcherAgent を新設**
2. **OWASP ASVS 5.0 ベースのセキュリティスキルファイルを追加**
3. **エンジニアリング原則スキルに56の法則・原則を収録**

いずれも「エージェントが正しい判断をするための知識ベース・ルールを充実させる」という方向性で一貫している。

---

## 1. FixAgent を6つの専門家エージェントに分割した

### 背景：単一エージェントの限界

以前は `FixAgent.agent.md` が1ファイルで「あらゆる種類のバグ修正」を担っていた。TypeScriptのコンパイルエラーも、ESLintの違反も、セキュリティ脆弱性も、すべて同じエージェントが受け持つ設計だった。

問題は、それぞれの修正が要求するスキルセット・検証手順・守るべきルールがまったく異なる点にある。型エラーを直す際の「ランタイム挙動を変えてはいけない」という制約と、テスト失敗を直す際の「実装が悪いのかテストが悪いのかを先に判断する」というプロセスは、同じエージェントに混在させると焦点がぼやける。

### 分割後の構成

| エージェント | 担当領域 |
|---|---|
| `FixDispatcherAgent` | 問題を分析してルーティングするオーケストレーター（コードは書かない） |
| `FixTypeAgent` | TypeScript コンパイルエラー（`TS2xxx`、型不一致、型アノテーション不足） |
| `FixLintAgent` | ESLint 違反（ルール別にコミットを分ける） |
| `FixTestAgent` | テスト失敗（実装 vs テストのどちらが誤りかを先に判定） |
| `FixFrontendAgent` | React コンポーネント・UI・Tailwind CSS のバグ |
| `FixBackendAgent` | Hono ハンドラ・ユースケース・リポジトリ・DB クエリのバグ |
| `FixSecurityAgent` | セキュリティ脆弱性・OWASP 違反・認証/認可バグ |

### FixDispatcherAgent の役割

`FixDispatcherAgent` はコードを一切書かない。受け取った問題を分析して、どの専門エージェントに委ねるかを決定するだけだ。

```
1. 問題の説明を読む
2. ルーティングテーブルで分類（単一 or 複数ドメイン）
3. 単一ドメイン → 該当エージェントに委譲
4. 複数ドメイン → 依存順に順次呼び出し
   - TypeScript エラー → Lint → テスト → Frontend/Backend/Security
5. 各エージェントの結果を集約して報告
```

同一ファイルを触る複数エージェントを並列実行してはいけないというルールも明文化されている。競合を防ぐためのシンプルな制約だ。

### 各専門エージェントの特徴

**FixTypeAgent** は「`as any` を使わない」「`@ts-ignore` は最終手段のみ」という厳格なルールを持つ。型エラーは型で直す。ランタイムロジックを変えてはいけない。

**FixTestAgent** の核心は「テスト失敗 = 実装が悪い、とは限らない」という判断軸だ。

```
テストが失敗したとき:
  仕様が明確か？
  ├── YES: 実装が仕様を満たしているか？
  │         ├── NO  → 実装を直す（TDDサイクル）
  │         └── YES → テストのアサーションが間違い → テストを直す
  └── NO:  ユーザーに曖昧さを報告して止まる
```

実装とテストを同じコミットで両方直してはいけない、というルールも重要だ。

**FixLintAgent** はルールカテゴリごとにコミットを切る。`no-unused-vars` の修正と `prefer-const` の修正を同じコミットに混ぜない。`eslint-disable` 全体無効化は禁止で、やむを得ず `eslint-disable-next-line` を使うときはなぜかの理由コメントが必須だ。

**FixSecurityAgent** は OWASP ASVS 5.0 スキルファイルを参照した上で修正を行う（後述）。バグ修正の前に失敗するセキュリティテストを書く TDD サイクルが必須となっている。

## 2. OWASP ASVS 5.0 ベースのセキュリティスキルファイルを追加した

### なぜスキルファイルとして持つのか

`FixSecurityAgent` がセキュリティ脆弱性を修正する際、「何が正しい実装か」の根拠が必要になる。その根拠をエージェントの定義ファイル内にすべて書き込むのではなく、カテゴリ別のスキルファイルとして分離した。

修正対象の脆弱性カテゴリに応じて、エージェントは該当スキルファイルを先に読んでから直す。

```
| 脆弱性カテゴリ                         | 参照スキルファイル               |
|---|---|
| インジェクション・XSS・SSRF・ファイルアップロード | security-input/SKILL.md     |
| CSP・Cookie・CSRF・CORS・HTTPヘッダー | security-frontend/SKILL.md  |
| パスワード・MFA・セッション管理           | security-authn/SKILL.md     |
| アクセス制御・IDOR・JWT               | security-authz/SKILL.md     |
| 暗号化・ハッシュ・鍵管理                 | security-cryptography/SKILL.md |
| シークレット・データ保護・キャッシュ         | security-config/SKILL.md    |
| SBOM・ログ・セキュアアーキテクチャ         | security-architecture/SKILL.md |
```

### security-authn（認証・セッション管理）の内容

ASVS の V6（認証）と V7（セッション管理）に対応している。主なルールを抜粋する。

**パスワード要件（V6.2）**

- 最小8文字（15文字以上を強く推奨）、最大64文字以上を許可
- 大文字/小文字/数字/記号の混在を強制しない
- パスワードは検証前に切り詰めたり変換したりしない（受け取ったそのままで比較する）
- ペーストとパスワードマネージャーの自動入力を許可する
- 新しいパスワードは上位3,000の一般的なパスワードと照合する
- 定期的なパスワード変更を要求しない（侵害されるまで有効）

**セッション管理（V7.2〜7.5）**

- セッショントークンは静的なAPIキーではなく、CSPRNG で生成した動的トークンを使う
- 最低128ビットのエントロピーを確保する
- 認証のたびに新しいセッショントークンを発行し、古いトークンは即座に無効化する
- ログアウト・有効期限切れ時はバックエンドでセッションを即座に無効化する

### security-input（入力セキュリティ）の内容

ASVS の V1・V2・V5 に対応。インジェクション、サニタイゼーション、バリデーション、ファイル処理を網羅している。

**インジェクション防止（V1.2）**

- SQL・HQL・NoSQL・Cypher のすべてにパラメータ化クエリまたは ORM を使う
- ユーザー入力をシェルコマンドに連結しない（パラメータ化されたOSクエリを使う）
- LDAP・XPath・LaTeX・CSV/数式インジェクションに対してもエスケープまたは許可リストを使う

**入力バリデーション（V2）**

- すべての入力は信頼できるサーバーサイドで検証する（クライアント側のバリデーションはUXのみ、セキュリティコントロールではない）
- ポジティブバリデーション（許可リスト方式）：型・形式・範囲・長さを確認してから使う

**ファイル処理（V5）**

- 許可された拡張子とコンテンツタイプのみ受け付ける。検証はマジックバイトで行い、拡張子だけに頼らない
- 圧縮アーカイブは展開前にZipボム攻撃を確認する（サイズとファイル数の制限）
- ユーザーが指定したファイル名からパスを構築しない（パストラバーサル、LFI、SSRFの防止）

### スキルファイル設計の利点

セキュリティ要件は改訂される。ASVS が更新されたときに、エージェント定義ファイルを編集するのではなく、スキルファイルだけを更新すればいい。エージェントの振る舞いとセキュリティ知識ベースが分離されているため、保守が楽になる。

## 3. エンジニアリング原則スキルに56の法則・原則を収録した

### 背景

`engineering-principles` スキルファイルはもともとKISS・DRY・YAGNIなどの基本的な設計原則だけを持っていた。エージェントがコードを書いたりレビューしたりする際に参照するリファレンスとして、体系的に整理された法則集を加えることにした。

### カテゴリ構成

追加した法則は8つのカテゴリに分類されている。

| カテゴリ | 収録内容（代表例） |
|---|---|
| **設計原則** | KISS・DRY・YAGNI・SRP・DI・OCP・SLAP・PIE |
| **アーキテクチャ・システム法則** | Conway's Law・Gall's Law・CAP定理・Postel's Law・Hyrum's Law |
| **コード品質法則** | Boy Scout Rule・Broken Windows Theory・Law of Demeter・Kernighan's Law |
| **チーム・組織法則** | Brooks's Law・Dunbar's Number・Bus Factor・Price's Law |
| **計画・見積もり法則** | Parkinson's Law・Hofstadter's Law・90-90ルール・Goodhart's Law |
| **テスト法則** | Testing Pyramid・Pesticide Paradox |
| **パフォーマンス法則** | Amdahl's Law・Gustafson's Law |
| **認知法則・メンタルモデル** | Dunning-Kruger Effect・Occam's Razor・Sunk Cost Fallacy・Pareto Principle |

### 注目の法則

**Hyrum's Law** はAPIを公開する際に特に意識したい法則だ。「ユーザーが十分に多ければ、APIのすべての観測可能な振る舞いに依存するコードが現れる。コントラクトに書かれていなくても。」つまり、バグを直すことすら破壊的変更になりうる。

**Gall's Law** はシステム設計の出発点として重要だ。「動く複雑なシステムは、動くシンプルなシステムから進化したものだ。最初から複雑なシステムを設計してもうまくいかない。」段階的に育てろ、という教えだ。

**Goodhart's Law** は指標設計で見落とされがちな罠を指摘する。「ある指標が目標になった瞬間、それは良い指標でなくなる。」テストカバレッジを目標にするとカバレッジだけを稼ぐテストが生まれる、という現象がまさにこれだ。

### SRP と DI の追加

既存の設計原則セクションに **SRP（単一責任の原則）** と **DI（依存性注入/依存性逆転）** も明示的に追加した。これらはリポジトリのバックエンドアーキテクチャ（Clean Architecture）と直接つながる原則であり、`FixBackendAgent` が Clean Architecture のレイヤー境界を守る際の根拠として参照できる。

### ソースリンクを除去した理由

初期のコミットではリンクが含まれていたが、その後のコミット（`736264e`〜`babd6bb`）でリンクをすべて削除している。スキルファイルはエージェントが実行時に読む「参照ドキュメント」であり、外部URLへの依存は壊れたリンクになりうる。法則の内容をファイル内に完結させ、エージェントが外部を参照せずに判断できるようにした。

## まとめ

今回のセッションで行った3つの強化をまとめると、いずれも「エージェントが個別のコンテキストに応じて正確に行動するための基盤整備」という一点に集約される。

- **FixAgent 分割** → 修正ドメインごとに専門特化させ、エージェントの責務を明確にした
- **OWASP ASVS 5.0 スキルファイル** → セキュリティ修正の根拠をカテゴリ別のスキルファイルとして外部化し、保守性を高めた
- **エンジニアリング原則56法則** → 設計・アーキテクチャ・チーム・認知の各レイヤーで参照できる体系的な知識ベースを構築した

`.github/` ディレクトリはコードではなく「エージェントへの指示と知識」が集まる場所だ。このインフラを充実させることが、AIエージェントが安定して良い仕事をするための土台になっている。
